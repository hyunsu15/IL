## 현재 깃 브랜치 전략의  문제

- 배포기준으로 브랜치 전략이 만들어져서 많이 복잡하다.
  - dev,test,main 까지 3가지 브랜치를 운영해야 한다. 인지적으로도 3가지 브랜치에서 개발해야 하며, feature 나 핫픽스등 여러가지 경우에서 고려해야 한다고 가정하면, 상당히 인지적으로 힘들어진다.
  

## 개인적으로 내리는 제안

우선 브랜치를 최소화한다.
브랜치 한개로 해도 충분해보이며, 더 안전하게는 2개까지 하는것이 좋아보임.

## 브랜치 한개일때 전략

메인만 있는 구성이다. 해당 방식은 trunked 기반 전략으로 알려진 방식이다.


main 에서 그때마다 feature, hotfix 등의 브랜치를 따서 그때그때 하는 방식이다.

```
main ──●──●──●──────●──●──────●──●──
        \      /      \      /
         ●────●        ●────●
      feature/주문취소   hotfix/NPE

           ↓ 태그로 배포 시점을 표시

main ──●──●──●──●──●──●──
          ↑     ↑     ↑
     (자동)   qa-0727  v2026.07.27
      dev배포  QA배포   운영배포
```

- 브랜치는 항상 `main` 하나뿐이고, 작업용 브랜치는 며칠 살다가 사라진다.
- 배포 단계는 브랜치가 아니라 **태그**로 구분한다.
- main 머지 시 dev 환경은 자동 배포되고, QA/운영은 태그를 찍어서 올린다.

### PR 정책 (Ship / Show / Ask)

변경의 성격에 따라 리뷰 시점을 다르게 가져가는 방식이다.

| 방식 | 설명 | 용도 |
|---|---|---|
| **Ship** | 리뷰 없이 바로 main | 오타, 문서, 자명한 수정 |
| **Show** | main에 머지하고 PR은 사후 리뷰용으로 열어둠 | 되돌리기 쉬운 변경 |
| **Ask** | 승인받고 머지 (일반 PR) | 나머지 전부 |

> 단, 브랜치 보호에서 "승인 필수"를 걸면 Ship/Show는 불가능해진다.
> 모든 변경에 승인이 필요한 조직이면 Ask만 쓰게 된다.

### 장점

**1. 인지 부담이 거의 없다**

"어디서 브랜치를 따지?", "이건 어디로 보내지?"를 고민할 일이 없다. 답이 항상 main이다.
핫픽스도 특별한 절차가 아니라 평소 작업과 똑같은 흐름이 된다.

**2. 승격 머지와 백머지가 아예 없다**

브랜치가 하나뿐이니 브랜치 간에 옮길 일이 없다.
지금 3브랜치에서 겪는 문제 대부분이 여기서 나오는 것들이라 통째로 사라진다.
- 승격할 때마다 나는 머지 충돌
- 핫픽스를 main에만 넣고 dev로 안 내려서 다음 릴리즈에 롤백되는 사고
- 브랜치끼리 코드가 벌어지는 드리프트

**3. 브랜치 간 코드 차이가 존재할 수 없다**

"dev랑 main이 지금 뭐가 다르지?"라는 질문 자체가 성립하지 않는다.

**4. 브랜치가 짧아서 충돌이 작다**

며칠 안에 합치니 base가 크게 안 움직인다.

**5. 신규 인원 온보딩이 쉽다**

설명할 규칙이 "main에서 따서 main으로 보낸다" 한 줄이다.

### 단점

배포라인은 조금 더 복잡해 질 수 있다.

아무래도 해당 전략은 우선 main은 dev 배포만을 하고, 따로 테스트 배포, 릴리즈 배포를 따로 만들어줘야 한다.

그리고 브랜치가 하던 안전장치를 다른 것이 대신해야 한다.


**1. 피처 플래그가 사실상 필수다**

미완성 기능도 main에 들어가야 하므로, 꺼둔 채로 머지할 수단이 필요하다.
"이번 릴리즈에서 이 기능만 빼자"를 브랜치가 아니라 설정으로 처리하게 된다.

**2. PR이 작고 리뷰가 빨라야 한다**

리뷰가 며칠씩 걸리면 브랜치가 길어지고, 그러면 이 전략의 전제가 깨진다.

## 브랜치 두개일때 전략

main, dev로만 구성된 상황입니다. 

```
dev  ──●──●──●──●──●──●──      (통합 / dev 자동배포)
             ↑        \
        qa-0727        \       (QA는 dev에 태그를 찍어서 배포)
                        ●      main (운영)
                        ↑
                   v2026.07.27
```

- 작업은 dev로 모으고, 릴리즈 시점에만 main으로 승격한다.
- test 환경은 브랜치 대신 **dev에 찍은 태그**로 배포한다.

### 장점

**1. 배포라인이 1개일때보다 쉽다**

test는 dev브랜치에 테그를 사용해서 test 배포를 할수 있게 하면 배포라인은 쉬워 질거 같다.
배포 대상을 브랜치가 아니라 태그로 지정하므로, 환경이 늘어도 파이프라인을 새로 만들 필요가 없다.

**2. dev가 완충 역할을 해준다**

main은 항상 "운영에 나가 있는 것"과 일치한다.
그래서 롤백 기준선이 명확하고, 핫픽스를 어디서 따야 하는지도 고민할 필요가 없다.

**3. 테스트가 아직 약해도 굴러간다**

브랜치 1개 전략의 가장 큰 진입 장벽이 완화된다.
main으로 넘어가기 전에 사람이 한 번 확인하는 단계가 남아 있기 때문이다.

**4. 지금 구조에서 옮기기 쉽다**

test 브랜치만 걷어내고 태그로 대체하면 된다.
dev와 main의 역할은 그대로 두면 되므로, 조직 합의 없이 팀 단위로 실행 가능하다.

**5. 승격이 한 번뿐이다**

dev → main 한 번이라 백머지도 main → dev 한 번이다.
3브랜치에서 두 단계씩 오가던 것에 비하면 관리 지점이 절반으로 준다.

**6. QA 대상이 불변이 된다**

태그는 고칠 수 없으므로 "QA 브랜치에서 바로 고치기"라는 유혹이 물리적으로 차단된다.
버그가 나오면 dev에서 고치고 새 태그를 찍는 것 외에 방법이 없다.

### 단점

**1. 승격 머지와 백머지가 여전히 남는다**

수는 줄었지만 없어지지는 않았다.
핫픽스를 main에 넣고 dev로 백머지하는 걸 빼먹으면, 다음 릴리즈 때 그 수정이 되돌아간다.
→ 백머지를 자동화하고, main에만 있는 커밋을 매일 감시해야 한다.

```bash
# main에 있는데 dev에 없는 실제 변경 = 백머지 누락
git rev-list --no-merges origin/main ^origin/dev
```

**2. dev와 main이 벌어질 수 있다**

승격이 밀리면 두 브랜치의 차이가 계속 커지고, 나중에 한 번에 합칠 때 충돌이 커진다.
미승격 커밋 수를 지표로 남겨두는 게 좋다.

**3. "전량 승격" 제약이 그대로다**

dev에 있는 건 다음 릴리즈에 전부 나간다.
"이건 빼고 나가자"를 하려면 결국 피처 플래그가 필요하다. 브랜치 1개 전략과 동일한 요구사항이다.
여기서 cherry-pick으로 우회하기 시작하면 이력이 갈라져서 상황이 3브랜치보다 나빠진다.

**4. 머지 방식 규칙이 두 가지 필요하다**

| 합칠 때 | 방식 | 이유 |
|---|---|---|
| feature/* → dev | Squash | 곧 삭제될 브랜치. 하나로 녹여서 revert를 쉽게 |
| dev → main | 머지 커밋 (`--no-ff`) | 둘 다 계속 살아있고, 언제 합쳐진지 그래프로 확인할 수 있어야 함. |

dev → main을 squash로 합치면 계보가 끊겨서 다음 승격 때 전부 충돌로 튀어나온다.
사람이 버튼으로 고르면 언젠가 실수하므로, 승격은 CI 잡으로 돌리는 게 안전하다.

**5. 태그 운영 규칙이 필요하다**

- `-a` (annotated) 로 찍는다 — 누가 언제 만들었는지 기록이 남는다
- 한번 찍은 태그는 옮기거나 지우지 않는다 — 움직이는 태그는 브랜치보다 나쁘다
- 태그 push는 자동이 아니다 (`--follow-tags`)
- 릴리즈 태그(`v*`)는 보호 규칙을 걸어 지정된 인원만 만들게 한다 → 승인 게이트 역할

## 개인적인 결론

배포라인을 구성을 잘할 수 있다면, 1번이 좋아보인다. 아무래도 승격머지등에서 자유롭고 규칙도 쉽기 때문에 개발자들은 편할 것같다. 대신 ci/cd가 다소 복잡해질 것 같다.

절충안으로는 2번이 그나마 나아보이고, 브랜치 3개나 로컬브랜치등의 전략들은 너무 복잡해져서 안하는 것이 나아보인다.
