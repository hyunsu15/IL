# 깃 브랜치 전략 개선 제안

## 현재 전략의 문제

브랜치 별로 배포하는 전략이다.

```
develop → dev 배포
test    → test 배포
main    → prod 배포
```

처음에는 직관적이지만, 시간이 지나면 다음 문제가 자주 생긴다.

### 환경마다 코드가 달라진다

develop, test, main의 커밋이 조금씩 달라지면 다음 상황이 생긴다.

- 개발 환경에서는 정상
- 테스트에서는 정상
- 운영에서만 오류

원인은 대개 "테스트에서 검증한 코드"와 "운영에 실제 배포된 코드"가 완전히 동일하지 않았기 때문이다.

### 머지·체리픽·충돌 비용이 증가한다

긴급 수정이 발생하면 흔히 다음 작업이 필요해진다.

```
hotfix를 main에 반영 → develop에도 반영 → test에도 반영
  → 충돌 해결 → 누락 여부 확인
```

**브랜치가 환경을 표현하면, 코드 동기화 자체가 운영 업무가 된다.**

### 배포 이력이 불명확해진다

"현재 운영은 정확히 어떤 버전인가?"라는 질문에 main 브랜치 HEAD만 봐서는 부족하다. 운영은 보통 다음을 알아야 한다.

| 알아야 하는 것 | 식별 수단 |
|---|---|
| 어느 커밋이 배포되었는가 | 릴리스 태그 `vX.Y.Z` |
| 어떤 이미지가 배포되었는가 | 이미지 digest (`sha256:...`) |
| 어떤 DB 마이그레이션이 적용되었는가 | 마이그레이션 버전 (Flyway/Liquibase 이력 테이블) |
| 어떤 설정값이 적용되었는가 | 설정 리포지터리 커밋 해시 또는 ConfigMap 리비전 |
| 언제 누가 승인했는가 | 배포 파이프라인 실행 기록 (승인자·시각) |

브랜치는 이 중 어느 것도 식별해주지 못한다. 브랜치는 "지금 어디를 개발 중인가"를 가리키는 포인터일 뿐, "무엇이 배포되었는가"의 기록이 아니다.

## 제안하는 방법

**단일 트렁크 + 활성 릴리스 브랜치 1개, 아티팩트 승격 배포**

핵심은 두 가지다.

1. **브랜치는 "무엇을 개발 중인가"만 나타낸다.** 환경을 표현하지 않는다. 상시 유지하는 브랜치는 main 하나뿐이고, release와 hotfix는 필요할 때 만들었다가 지운다.
2. **환경 간 배포는 머지가 아니라 동일 아티팩트의 승격으로 한다.** test에서 검증한 이미지와 prod에 올라가는 이미지가 digest 단위로 같다. 환경별로 다시 빌드하지 않는다.

### 이 방식의 한계

먼저 밝혀둔다. 이 방식도 백머지를 없애지는 못한다. release나 hotfix에서 고친 버그는 여전히 main에 반영해야 한다.

달라지는 것은 다음이다.

- **영구 브랜치 간 드리프트가 사라진다.** release는 릴리스 1회 동안만 살고 지워지므로, "develop과 main이 지금 뭐가 다른가"라는 상시 질문 자체가 없어진다.
- **누락 위험 구간이 상시에서 릴리스 시점 1회로 압축된다.**
- 압축된 그 1회는 CI로 강제할 수 있다. (아래 [백머지 강제](#releasehotfix--main-반영-강제) 참고)

즉 문제가 사라지는 게 아니라 **감시 가능한 크기로 줄어든다.** 현재 3브랜치 구조는 이 검사를 상시로 돌려야 하지만, 이 방식은 릴리스 종료 시점 한 번이면 된다.

## 브랜치 역할
예시이며, 무조건 이대로 할 필요는 없다.

| 브랜치 | 역할 | 수명 |
|---|---|---|
| `main` | 다음 버전 개발을 계속하는 곳 | 영구 |
| `release/x.y.z` | 배포 후보로 고정한 버전의 버그·안정화만 처리 | 릴리스 1회 |
| `hotfix/x.y.z` | 이미 운영 중인 버전의 긴급 장애만 처리 | 장애 대응 1회 |
| `feature/*` | 개별 기능 개발 | 5영업일 이내 |

```
main
A ─ B ─ C ─ D ─ E ───────── M ─ F
        │                   ↑
        └ release/1.3.0     │
            R1 ─ R2 ────────┘
                 │
               v1.3.0
```

- `C` : release/1.3.0을 자른 기준 커밋
- `D`, `E`, `F` : 다음 릴리스용 신규 기능·일반 수정
- `R1`, `R2` : 1.3.0 QA 중 발견된 버그 수정
- `M` : release를 main에 되돌린 머지 커밋 (`--no-ff`)
- `v1.3.0` : 실제 운영에 배포된 커밋(R2)에 붙인 태그

`M` 머지가 끝나야 release/1.3.0을 삭제할 수 있다. 이 화살표가 이 전략의 생명선이다.

## main에 올리는 기준

**미완성 기능은 main에 커밋하지 않는다.** main에 머지되는 변경은 그 자체로 완성되어, 언제 릴리스되어도 문제가 없는 상태여야 한다.

이 규칙이 필요한 이유는 릴리스 브랜치를 자르는 시점 때문이다. `release/x.y.z`는 특정 커밋에서 잘리므로, 그 시점 main에 미완성 기능이 섞여 있으면 그대로 릴리스 후보에 포함된다. 빼내려면 revert나 cherry-pick이 필요해지고, 그 순간 이력이 갈라져서 지금보다 나빠진다.

### 대가와 전제 조건

미완성을 main에 안 올리면 feature 브랜치가 길어지고, 길어지면 머지 충돌이 커진다. 이 규칙을 유지하려면 다음이 함께 가야 한다.

- **기능을 작게 쪼갠다.** "주문 취소 기능" 하나가 2주짜리라면, 릴리스 가능한 단위로 나눠서 여러 번 머지한다. 이게 안 되면 규칙 자체가 유지되지 않는다.
- **feature 브랜치는 main을 자주 따라간다.** 최소 하루 1회 main을 머지해서 드리프트를 줄인다.
- **브랜치 수명 상한을 둔다.** 5영업일을 넘기면 더 쪼갤 수 있는지 다시 본다.

> 업계에서 흔히 쓰는 대안은 피처 플래그로, 미완성 기능도 꺼둔 채 main에 넣는 방식이다.
> 이 제안에서는 채택하지 않는다. 플래그 자체가 관리 대상이 되고(제거 시점을 놓치면
> 코드가 분기투성이가 된다), 플래그마다 테스트해야 할 조합이 늘어나기 때문이다.
> 대신 "작게 쪼개기"에 의존한다.

## 환경별 배포 기준

| 환경 | 배포 대상 | 트리거 | 목적 |
|---|---|---|---|
| dev | main에서 빌드한 최신 이미지 | main 머지 시 자동 | 개발 기능의 빠른 통합 확인 |
| test | 특정 release/hotfix 후보 이미지 | 버튼 또는 승인으로 선택 | QA, 회귀 테스트, 릴리스 검증 |
| prod | test에서 검증한 **동일 digest** | 승인 후 승격 | 운영 |

- test는 검증 중에 다른 배포로 덮어쓰지 않도록 버전을 고정한다.
- **prod는 새로 빌드하지 않는다.** test에서 검증한 이미지 digest를 그대로 올린다. 재빌드하면 "검증한 것과 배포한 것이 다르다"는 원래 문제가 되돌아온다.
- prod 배포 후 실제 배포된 커밋에 `vX.Y.Z` 태그를 남긴다.

## 릴리스 절차

1. 이번 배포에 포함할 변경이 모두 main에 들어간 커밋에서 `release/x.y.z`를 만든다.
2. release 브랜치에는 신규 기능을 넣지 않는다. QA에서 발견된 버그 수정, 설정 보완, 배포 안정화 변경만 반영한다.
3. release의 최종 커밋으로 빌드한 이미지를 test에 배포해 검증을 완료한다.
4. test에서 검증한 **동일 이미지 digest**를 승인 후 prod에 배포한다.
5. 실제 배포된 커밋에 `vX.Y.Z` 태그를 만든다.
6. release를 main에 `--no-ff`로 머지한다.
7. 백머지 검사를 통과하면 release 브랜치를 삭제한다.

6~7번은 릴리스 종료 잡에서 자동 처리한다. 다음 릴리스(1.4.0)도 같은 절차를 반복한다.

브랜치를 삭제해도 `vX.Y.Z` 태그와 main의 머지 이력이 남으므로, 필요하면 태그에서 hotfix 브랜치를 다시 만들 수 있다.

### release에만 남은 변경 처리

**선별 반영은 하지 않는다. 6번에서 release 전체를 머지한다.**

머지는 브랜치 단위라 일부만 골라 담을 수 없고, `--no-ff` 머지를 하는 순간 release의 모든 커밋이 main에서 도달 가능해진다. 반대로 특정 커밋을 의도적으로 빼면 7번의 도달 가능성 검사가 영원히 실패해서 브랜치를 못 지운다. 예외 목록을 만들면 사람 판단을 없애려고 넣은 검사에 사람 판단을 다시 넣는 셈이 된다.

그래서 판단 지점을 "main에 반영할지 말지"가 아니라 **"머지한 뒤 main에서 어떻게 처리할지"** 로 옮긴다.

| release에만 남은 변경 | main 처리 | 검사 |
|---|---|---|
| 다음 버전에도 필요한 버그 수정 | 머지된 그대로 둔다 | 통과 |
| main에 이미 동등한 수정이 있음 | 충돌나면 main 쪽을 채택한다 | 통과 |
| 버전 번호·배포 설정 등 main에 불필요한 변경 | 머지 후 main에서 `git revert`로 되돌린다 | 통과 |

세 번째가 특히 중요하다. "의도적으로 반영하지 않음"은 이력에 아무것도 남기지 않아서, 6개월 뒤에 보면 누락인지 의도인지 구분할 수 없다. **revert 커밋은 왜 안 가져갔는지가 커밋 메시지로 남는다.**

> cherry-pick으로 골라 담고 싶다면 검사를 patch-id 기반(`git cherry -v main release/1.3.0`)으로
> 바꿔야 한다. 다만 충돌을 다르게 해결했거나 squash가 끼면 오탐이 나서 검사 신뢰도가 떨어진다.
> 얻는 것이 "main 이력이 깔끔해진다" 정도라 값이 맞지 않는다.

### 세 번째 경우를 애초에 없애기

release 브랜치에 버전 번호나 배포 설정 커밋이 자꾸 생긴다면, 예외 규칙이 필요하다는 신호가 아니라 **버전과 설정이 코드에 섞여 있다는 신호**다.

- **버전 번호를 파일에 커밋하지 않는다.** 태그에서 파생시키면(`git describe`, Gradle nebula-release 등) 버전 bump 커밋 자체가 생기지 않는다. `build.gradle`에 `1.3.0`을 박는 순간, main은 `1.4.0-SNAPSHOT`이라 매 릴리스마다 충돌이 예약된다.
- **배포 설정을 애플리케이션 리포에서 분리한다.** 설정 리포를 따로 두면 release 브랜치에 배포 설정 커밋이 올라올 일이 없다. 앞의 "설정값은 설정 리포지터리 커밋 해시로 식별한다"와도 일관된다.

이 둘을 적용하면 세 번째 경우는 일회성 안정화 변경 정도만 남는다. 그 정도는 revert로 충분하다.

## hotfix 흐름

hotfix 브랜치는 main이 아니라 **운영 태그**에서 자른다.

```bash
git switch -c hotfix/1.3.1 v1.3.0
```

이렇게 하면 main에 이미 들어간 다음 릴리스용 변경(위 그림의 `D`, `E`, `F`)이 딸려 들어가지 않는다. 과거 버전을 복구하기 위해 rebase나 cherry-pick을 쓸 필요가 없다.

### 배포 경로

긴급 상황에서 무엇을 생략할지는 미리 정해둬야 한다. 그 자리에서 정하면 매번 달라진다.

| 구분 | 경로 | 승인 |
|---|---|---|
| 일반 hotfix | 빌드 → test 배포 → 축소 회귀 검증 → 동일 digest prod 승격 | 평시와 동일 |
| 긴급 (서비스 중단) | 빌드 → test 스모크 테스트만 → prod 승격 | 지정 승인자 1인 구두 승인 후 사후 기록 |

**test를 완전히 건너뛰는 경로는 만들지 않는다.** 이미지를 한 번도 띄워보지 않은 채 prod에 올리면 롤백 대상도 불분명해지기 때문이다. 스모크 테스트는 몇 분이면 끝난다.

hotfix 배포 후에도 릴리스 절차 5~7번(태그 → main 머지 → 검사 → 삭제)을 동일하게 밟는다.

## release/hotfix → main 반영 강제

이 전략의 유일한 실패 지점은 **release나 hotfix에서 고친 것을 main에 반영하지 않는 것**이다. 반영을 놓치면 다음 릴리스에서 그 수정이 조용히 사라진다. 운영 롤백처럼 보이는 최악의 버그다.

사람이 기억하는 규칙은 언젠가 깨지므로 CI로 막는다.

### 확인 명령

release에 있으나 main에 없는 커밋을 세는 것으로 판별한다.

```bash
git fetch origin --prune --tags
git rev-list --no-merges origin/release/1.3.0 ^origin/main
```

출력이 비어 있으면 반영 완료, 커밋 해시가 나오면 미반영이다.

### CI 게이트

```bash
#!/usr/bin/env bash
set -euo pipefail

BRANCH="$1"   # 예: release/1.3.0 또는 hotfix/1.3.1

git fetch origin --prune --tags

if git rev-list --no-merges "origin/${BRANCH}" ^origin/main | grep -q .; then
  echo "main에 반영되지 않은 커밋이 있습니다:"
  git log --no-merges --oneline "origin/${BRANCH}" ^origin/main
  exit 1
fi

echo "main 반영 완료. 브랜치를 삭제할 수 있습니다."
```

이 스크립트를 두 곳에 건다.

1. **릴리스 종료 잡** — 통과해야만 release 브랜치를 삭제한다. 삭제까지 이 잡에서 자동 처리해서 사람이 손댈 여지를 없앤다.
2. **일 1회 스케줄 잡** — 열려 있는 모든 `release/*`, `hotfix/*`를 검사한다. 릴리스가 길어질 때 방치되는 걸 막는다.

### 머지 방식

`release`/`hotfix` → `main`은 반드시 머지 커밋으로 합친다.

```bash
git switch main
git merge --no-ff release/1.3.0
```

squash로 합치면 커밋 계보가 끊겨서 위 `rev-list` 검사가 항상 "미반영"으로 나오고, 다음 릴리스 때 이미 반영한 변경이 전부 충돌로 다시 튀어나온다.

`feature` → `main`은 squash로 합쳐도 무방하다. 곧 삭제될 브랜치이고, 하나로 녹여두면 revert가 쉽다.

## 전환 계획

한 번에 바꾸지 않는다. **파이프라인을 먼저 만들고, 브랜치는 마지막에 없앤다.** 순서를 반대로 하면 전환 도중에 배포할 수단이 사라진다.

### 0단계 — 아티팩트 승격 파이프라인 구축

현재 브랜치 구조를 그대로 둔 채 다음을 만든다. 브랜치 변경이 없으므로 팀 합의 없이 착수할 수 있다.

- 빌드 잡이 이미지를 만들고 digest를 기록한다. 커밋 해시를 이미지 라벨에 넣는다.
- test/prod 배포 잡이 "브랜치"가 아니라 "digest"를 입력으로 받도록 바꾼다.
- 승인 게이트를 넣고 승인자·시각을 기록한다.
- 릴리스 태그 생성을 파이프라인에 넣는다.

이 단계가 끝나면 기존 방식으로 운영하면서도 승격 배포를 시험해볼 수 있다.

### 1단계 — test 브랜치 제거

- 다음 릴리스부터 `release/x.y.z`를 잘라 test 배포에 사용한다.
- test 브랜치는 배포 트리거에서 제외하고, 1개 릴리스 주기 동안 읽기 전용으로 남겨둔다.
- 백머지 검사 스크립트를 이 시점에 투입한다.

### 2단계 — develop 브랜치 제거

- develop에만 있는 커밋이 없는지 확인하고 main에 반영한다.

  ```bash
  git rev-list --no-merges origin/develop ^origin/main
  ```

- feature 브랜치를 main에서 자르고 main으로 보내도록 바꾼다.
- develop을 배포 트리거에서 제외하고, dev 환경은 main 머지 시 자동 배포로 전환한다.
- 진행 중이던 작업은 기준 브랜치를 main으로 리베이스한다. **전환 시점을 스프린트 경계에 맞추면 이 작업이 거의 없어진다.**

### 3단계 — 안정화

- 2~3회 릴리스 동안 백머지 누락 건수, 롤백 발생 여부, 릴리스 소요 시간을 지표로 본다.
- 문제가 없으면 develop/test 브랜치를 삭제한다.

### 롤백 계획

전환 중 문제가 생기면 브랜치가 아직 살아 있으므로 기존 파이프라인으로 되돌린다. 0단계에서 만든 승격 잡은 그대로 두고 트리거만 원복하면 된다. **브랜치 삭제를 3단계까지 미루는 이유가 이것이다.**

### 확인이 필요한 항목

| 항목 | 확인 대상 |
|---|---|
| 레지스트리에서 digest 기반 배포가 가능한지 | 인프라 |
| DB 마이그레이션 롤백 정책 (승격 시 스키마 호환성) | DBA |
| 릴리스 태그 생성 권한을 누구에게 줄지 | 조직 |
| 긴급 hotfix 승인자 지정 | 조직 |
| 전환 시작 시점 (스프린트 경계 권장) | 팀 |

## 정리

- 브랜치로 환경을 표현하는 것을 그만두고, 같은 이미지를 승격해서 배포한다.
- 상시 브랜치는 main 하나. release와 hotfix는 목적을 다하면 지운다.
- 백머지는 남지만, 릴리스 시점 1회로 압축되고 CI가 막아준다.
- 미완성 기능은 main에 올리지 않는다. 대신 작업을 작게 쪼갠다.
- 파이프라인을 먼저 만들고 브랜치를 나중에 없앤다.
