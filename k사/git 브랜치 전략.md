# 깃 브랜치 전략 개선 제안

## 현재 전략의 문제

브랜치 별로 배포하는 전략이다.

```
develop → dev 배포
test    → test 배포
main    → prod 배포
```

처음에는 직관적이지만, 시간이 지나면 다음 문제가 자주 생긴다.

### 환경마다 코드가 달라진다

develop, test, main의 커밋이 조금씩 달라지면 다음 상황이 생긴다.

- 개발 환경에서는 정상
- 테스트에서는 정상
- 운영에서만 오류

원인은 대개 "테스트에서 검증한 코드"와 "운영에 실제 배포된 코드"가 완전히 동일하지 않았기 때문이다.

### 머지·체리픽·충돌 비용이 증가한다

긴급 수정이 발생하면 흔히 다음 작업이 필요해진다.

```
hotfix를 main에 반영 → develop에도 반영 → test에도 반영
  → 충돌 해결 → 누락 여부 확인
```

**브랜치가 환경을 표현하면, 코드 동기화 자체가 운영 업무가 된다.**

### 배포 이력이 불명확해진다

"현재 운영은 정확히 어떤 버전인가?"라는 질문에 main 브랜치 HEAD만 봐서는 부족하다. 운영은 보통 다음을 알아야 한다.

| 알아야 하는 것 | 식별 수단 |
|---|---|
| 어느 커밋이 배포되었는가 | 릴리스 태그 `vX.Y.Z` |
| 어떤 이미지가 배포되었는가 | 이미지 digest (`sha256:...`) |
| 어떤 DB 마이그레이션이 적용되었는가 | 마이그레이션 버전 (Flyway/Liquibase 이력 테이블) |
| 어떤 설정값이 적용되었는가 | 설정 리포지터리 커밋 해시 또는 ConfigMap 리비전 |
| 언제 누가 승인했는가 | 배포 파이프라인 실행 기록 (승인자·시각) |

브랜치는 이 중 어느 것도 식별해주지 못한다. 브랜치는 "지금 어디를 개발 중인가"를 가리키는 포인터일 뿐, "무엇이 배포되었는가"의 기록이 아니다.

## 제안하는 방법

**main 브랜치 + dev 브랜치 1개, 아티팩트 승격 배포**

핵심은 두 가지다.

1. **브랜치는 "무엇을 개발 중인가"만 나타낸다.** 환경을 표현하지 않는다. 상시 유지하는 브랜치는 `main`과 `dev` 둘뿐이고, hotfix와 feature는 필요할 때 만들었다가 지운다.
2. **환경 간 배포는 머지가 아니라 동일 아티팩트의 승격으로 한다.** test에서 검증한 이미지와 prod에 올라가는 이미지가 digest 단위로 같다. 환경별로 다시 빌드하지 않는다.

### 이 방식의 한계

먼저 밝혀둔다. 이 방식이 모든 문제를 없애지는 않는다.

**1. QA 동결을 브랜치가 아니라 파이프라인이 한다**

릴리스 브랜치를 만들지 않으므로, "이번에 나갈 것"은 **후보 커밋 SHA**로만 고정된다. Git 저장소만 봐서는 "지금 QA 중인 게 뭐냐"를 알 수 없고, 파이프라인 기록이 진실의 원천이 된다. 파이프라인이 후보 SHA와 이미지 digest를 확실히 붙들고 있어야 이 전략이 성립한다.

**2. QA 중 발견된 버그 수정이 이 모델의 가장 아픈 지점이다**

수정할 브랜치가 dev밖에 없다. dev에서 고치면 후보 커밋 이후에 들어온 다른 변경까지 함께 딸려온다. 그래서 후보를 다시 잡아야 하고, QA도 다시 돌아간다.

완화 방법은 두 가지다.

- QA 기간에는 dev 머지를 자제한다는 합의를 둔다 (기간이 짧을 때만 가능)
- 후보 이후 변경이 많으면 후보 커밋에서 임시 브랜치를 판다 — 사실상 릴리스 브랜치의 부활이다

**QA 기간 × dev 머지 빈도**가 이 모델의 수용 한계를 결정한다. QA가 2주씩 걸리면 릴리스 브랜치를 도입하는 편이 낫다.

**3. "전량 승격" 제약이 있다**

후보 커밋 시점까지의 dev 변경은 전부 나간다. "이건 빼고 나가자"가 안 된다. 그래서 **미완성 기능은 dev에 올리지 않는다**는 규칙이 전제된다.

**4. 백머지가 완전히 사라지지는 않는다**

`dev → main`은 항상 한 방향이라 안전하지만, hotfix는 `main`에 먼저 들어가므로 `dev`로 내려보내야 한다. 감시 지점이 하나 남는다. 다만 현재 3브랜치 구조가 상시 세 방향을 감시해야 하는 것에 비하면 크게 줄어든다.

**5. main HEAD가 곧 현재 운영은 아니다**

알파·베타 릴리스도 main에 태그로 남으므로, "지금 운영에 뭐가 떠 있나"는 **최신 정식 릴리스 태그**로 확인해야 한다. hotfix를 딸 때 특히 중요하다.

## 브랜치 역할
예시이며, 무조건 이대로 할 필요는 없다.

| 브랜치 | 역할 | 수명 |
|---|---|---|
| `main` | 베타,알파 포함한 운영 버전 | 영구 |
| `dev` | 다음버전 개발 | 영구 |
| `hotfix/x.y.z` | 운영 버전의 긴급 장애만 처리 | 장애 대응 1회 |
| `feature/*` | 개별 기능 개발 | 기능개발 완료까지(최대한 짧게) |

### 평상시 흐름

```
feature/*        ●──●
                ╱     ╲
dev   ──●──●───●───────●──●──[C1]──●──●──●──[C2]──●──
                              ╲                ╲
                               ╲ 승격           ╲ 승격
                                ╲                ╲
main  ───────────────────────────●────────────────●──
                                 │                │
                              v1.3.0           v1.4.0
```

- **`dev`** — feature가 모이는 통합 브랜치. 머지되면 dev 환경에 자동 배포된다. 다음 버전이 여기서 자란다.
- **`[C1]`, `[C2]`** — **후보 커밋**. "이번 배포에 나갈 것"을 고정한 지점이다. 브랜치를 자르지 않고 SHA만 파이프라인에 기록한다.
- **승격** — 후보 커밋이 test·prod 검증을 통과하면 그 커밋을 main에 머지한다. dev의 끝이 아니라 **후보 커밋**을 머지하는 것이 핵심이다.

  ```bash
  git merge --no-ff <후보커밋SHA>
  ```

- **`main`** — 배포된 것만 들어온다. 직접 커밋하지 않고 승격 머지와 hotfix만 받는다. 그래서 main 이력이 곧 배포 이력이 된다.
- 후보 커밋 이후 dev에 쌓인 커밋은 잔여물이 아니라 **다음 릴리스 몫**이다. 그대로 두면 된다.

### hotfix 흐름

```
main  ──●(v1.3.0)────────────────●(v1.3.1)──
         ╲                      ╱ ╲
          hotfix/1.3.1 ──●─────╯   ╲
                                    ╲ 백머지
dev   ──●──●──●──●──●──●──●──●───────●──
```

- hotfix는 `main` HEAD가 아니라 **운영에 떠 있는 태그**에서 자른다.
- 배포 후 main에 머지하고, **반드시 dev로 내려보낸다.** 이 백머지가 이 전략의 유일한 실패 지점이다.

## 환경별 배포 기준

| 환경 | 배포 대상 | 트리거 | 목적 |
|---|---|---|---|
| dev | dev에서 빌드한 최신 이미지 | dev 머지 시 자동 | 개발 기능의 빠른 통합 확인 |
| test | 특정 main 후보 이미지 | 버튼 또는 승인으로 선택 | QA, 회귀 테스트, 릴리스 검증 |
| prod | test에서 검증한 **동일 digest** | 승인 후 승격 | 운영 |

- test는 검증 중에 다른 배포로 덮어쓰지 않도록 버전을 고정한다.
- **prod는 새로 빌드하지 않는다.** test에서 검증한 이미지 digest를 그대로 올린다. 재빌드하면 "검증한 것과 배포한 것이 다르다"는 원래 문제가 되돌아온다.
- prod 배포 후 실제 배포된 커밋에 `vX.Y.Z` 태그를 남긴다.

## 릴리스 절차

브랜치를 자르는 대신 **후보 커밋을 고정**하는 것이 이 절차의 핵심이다.

1. dev에서 이번 배포에 포함할 변경이 모두 들어간 커밋을 **후보 커밋**으로 정한다. 브랜치를 만들지 않고 SHA를 파이프라인에 기록한다.
2. 후보 커밋으로 이미지를 빌드한다. 커밋 해시를 이미지 라벨에 넣는다.
3. 그 이미지를 test에 배포해 QA를 완료한다. 검증 중 dev가 움직여도 후보는 바뀌지 않는다.
4. 통과하면 **동일 digest**를 승인 후 prod에 승격 배포한다.
5. 실제 빌드·배포된 커밋(= 후보 커밋)에 `vX.Y.Z` 태그를 만든다.
6. 후보 커밋을 main에 `--no-ff`로 머지한다.

   ```bash
   git switch main
   git merge --no-ff <후보커밋SHA> -m "Release v1.4.0"
   ```

7. main에 hotfix가 들어간 적이 있으면 dev로 내려보낸다.

5~6번은 릴리스 종료 잡에서 자동 처리한다. 태그를 머지 커밋이 아니라 후보 커밋에 붙이는 이유는, **그 커밋이 실제로 빌드된 커밋**이기 때문이다. `git describe`도 그 기준으로 동작한다.

### QA 중 버그가 나왔을 때

릴리스 브랜치가 없으므로 **dev에서 고친다.** 그리고 후보 커밋을 다시 잡는다.

이때 후보 이후 dev에 들어온 변경까지 함께 나가게 되므로, 다음 중 하나를 선택한다.

| 상황 | 처리 |
|---|---|
| 후보 이후 dev 변경이 적음 | 새 후보로 다시 잡고 QA 재실행 |
| 후보 이후 dev 변경이 많음 | 후보 커밋에서 임시 브랜치를 파서 거기서 고침 |
| QA가 길어질 것이 예상됨 | 애초에 릴리스 브랜치 도입을 검토 |

두 번째를 자주 하게 된다면 그건 **릴리스 브랜치가 필요하다는 신호**다. 규칙을 정교하게 만들 게 아니라 모델을 바꿔야 한다.

### 승격이 밀리는 것을 감시한다

dev와 main이 벌어지면 승격 머지의 충돌이 커진다. 미승격 커밋 수를 지표로 본다.

```bash
git rev-list --count --no-merges origin/dev ^origin/main
```

이 값이 계속 커지면 릴리스 주기가 너무 길다는 뜻이다.

## hotfix 흐름

### 어디서 자르는가

**운영에 실제로 떠 있는 태그**에서 자른다. `main` HEAD가 아니다. main에는 알파·베타나 아직 prod에 안 나간 것이 있을 수 있다.

```bash
# 0. 운영에 뭐가 떠 있는지 먼저 확인
git fetch origin --tags
git tag --sort=-v:refname | head -5

# 1. 그 태그에서 브랜치
git switch -c hotfix/1.3.1 v1.3.0
```

태그 목록만 믿지 않는다. 롤백 중이거나 배포가 실패했을 수 있으므로, 지금 떠 있는 이미지의 커밋 라벨에서 직접 확인하는 것이 정확하다.

```bash
docker inspect <이미지>@sha256:... \
  --format '{{index .Config.Labels "org.opencontainers.image.revision"}}'
```

hotfix가 연달아 나면 항상 **가장 최근 운영 태그**에서 자른다. `v1.3.1`을 배포한 뒤 또 문제가 생기면 `v1.3.1`에서 `hotfix/1.3.2`를 만든다.

### 배포 경로

긴급 상황에서 무엇을 생략할지는 미리 정해둬야 한다. 그 자리에서 정하면 매번 달라진다.

| 구분 | 경로 | 승인 |
|---|---|---|
| 일반 hotfix | 빌드 → test 배포 → 축소 회귀 검증 → 동일 digest prod 승격 | 평시와 동일 |
| 긴급 (서비스 중단) | 빌드 → test 스모크 테스트만 → prod 승격 | 지정 승인자 1인 구두 승인 후 사후 기록 |

**test를 완전히 건너뛰는 경로는 만들지 않는다.** 이미지를 한 번도 띄워보지 않은 채 prod에 올리면 롤백 대상도 불분명해지기 때문이다. 스모크 테스트는 몇 분이면 끝난다.

### 배포 후 처리

```bash
# 배포된 커밋에 태그
git tag -a v1.3.1 -m "hotfix: 결제 취소 NPE"
git push origin v1.3.1

# main에 반영
git switch main
git merge --no-ff hotfix/1.3.1 && git push

# dev에 반영 — 빠뜨리면 다음 릴리스에서 버그가 되살아난다
git switch dev
git merge --no-ff main && git push

# 반영 확인 후 삭제
git branch -a --contains hotfix/1.3.1
git push origin --delete hotfix/1.3.1
```

hotfix에는 **그 장애의 수정만** 넣는다. 리팩터링이나 다른 버그 수정을 얹지 않는다.

## main → dev 반영 강제

이 전략의 유일한 실패 지점은 **hotfix를 main에 넣고 dev에 내려보내지 않는 것**이다. 놓치면 다음 릴리스에서 그 수정이 조용히 사라진다. 운영 롤백처럼 보이는 최악의 버그다.

`dev → main`은 항상 한 방향이므로 감시할 필요가 없다. **감시 대상은 이 한 방향뿐이다.**

### 확인 명령

main에 있으나 dev에 없는 커밋을 세는 것으로 판별한다.

```bash
git fetch origin --prune --tags
git rev-list --no-merges origin/main ^origin/dev
```

출력이 비어 있으면 반영 완료, 커밋 해시가 나오면 미반영이다.

### CI 게이트

```bash
#!/usr/bin/env bash
set -euo pipefail

git fetch origin --prune --tags

if git rev-list --no-merges origin/main ^origin/dev | grep -q .; then
  echo "dev에 반영되지 않은 main 커밋이 있습니다:"
  git log --no-merges --oneline origin/main ^origin/dev
  exit 1
fi

echo "dev 반영 완료."
```

거는 곳은 두 군데다.

1. **hotfix 종료 잡** — 통과해야만 hotfix 브랜치를 삭제한다. 삭제까지 이 잡에서 자동 처리해서 사람이 손댈 여지를 없앤다.
2. **일 1회 스케줄 잡** — main에만 있는 커밋이 남아 있는지 검사한다.

**처음부터 차단할 필요는 없다.** 2단계로 나누는 편이 조직 설득에 유리하다.

- **1단계 (관측)** — 스케줄 잡이 미반영 커밋 수를 알리기만 한다. 아무것도 막지 않는다.
- **2단계 (강제)** — 2~3회 릴리스를 돌려보고 실제로 누락이 발생하면 그때 차단한다.

*"이거 필요합니다"* 보다 *"지난 3번 중 2번 누락됐습니다"* 가 설득력이 있다. 다만 강제하지 않으면 브랜치 자동 삭제도 못 한다는 점은 감안한다.

### 머지 방식

| 머지 | 방식 | 이유 |
|---|---|---|
| `dev`(후보 커밋) → `main` | `--no-ff` | 승격 이력이 그래프에 남아야 한다 |
| `main` → `dev` (hotfix 백머지) | `--no-ff` | 계보가 이어져야 검사가 동작한다 |
| `feature/*` → `dev` | squash 가능 | 곧 삭제될 브랜치. 하나로 녹여두면 revert가 쉽다 |

squash로 합치면 커밋 계보가 끊겨서 위 `rev-list` 검사가 항상 "미반영"으로 나오고, 다음 머지 때 이미 반영한 변경이 전부 충돌로 다시 튀어나온다. **cherry-pick도 같은 이유로 피한다** — SHA가 달라져서 `git branch --contains`로 추적할 수 없게 된다.

### 릴리스 이력 읽기

main 줄기만 보면 릴리스 이력이 된다.

```bash
git log --oneline --first-parent main
```

dev의 개별 커밋이 감춰지고 "언제 무엇이 배포되었나"만 남는다. 이 뷰를 기본 조회 방식으로 쓴다.

## 버전과 설정을 코드에서 분리한다

승격 머지에 불필요한 커밋이 섞이지 않게 하려면 두 가지를 먼저 정리해야 한다.

- **버전 번호를 파일에 커밋하지 않는다.** 태그에서 파생시키면(`git describe`, Gradle nebula-release 등) 버전 bump 커밋 자체가 생기지 않는다. `build.gradle`에 `1.3.0`을 박는 순간, dev는 `1.4.0-SNAPSHOT`이라 매 릴리스마다 충돌이 예약된다.
- **배포 설정을 애플리케이션 리포에서 분리한다.** 설정 리포를 따로 두면 배포 설정 커밋이 승격에 섞이지 않는다. 앞의 "설정값은 설정 리포지터리 커밋 해시로 식별한다"와도 일관된다.

이 둘을 적용하면 dev에는 순수한 코드 변경만 남아서, 후보 커밋을 어디로 잡든 부담이 없어진다.

## 전환 계획

한 번에 바꾸지 않는다. **파이프라인을 먼저 만들고, 브랜치는 마지막에 정리한다.** 순서를 반대로 하면 전환 도중에 배포할 수단이 사라진다.

기존 `develop`이 그대로 `dev` 역할을 이어받으므로 전환 폭이 크지 않다.

### 0단계 — 아티팩트 승격 파이프라인 구축

현재 브랜치 구조를 그대로 둔 채 다음을 만든다. 브랜치 변경이 없으므로 팀 합의 없이 착수할 수 있다.

- 빌드 잡이 이미지를 만들고 digest를 기록한다. 커밋 해시를 이미지 라벨에 넣는다.
- test/prod 배포 잡이 "브랜치"가 아니라 "digest"를 입력으로 받도록 바꾼다.
- 후보 커밋 SHA를 파이프라인이 기록하고 조회할 수 있게 한다.
- 승인 게이트를 넣고 승인자·시각을 기록한다.
- 릴리스 태그 생성을 파이프라인에 넣는다.

이 단계가 끝나면 기존 방식으로 운영하면서도 승격 배포를 시험해볼 수 있다.

### 1단계 — test 브랜치 제거

- 다음 릴리스부터 **후보 커밋의 이미지**를 test에 배포한다.
- test 브랜치는 배포 트리거에서 제외하고, 1개 릴리스 주기 동안 읽기 전용으로 남겨둔다.
- 백머지 검사 스크립트를 관측 모드로 투입한다.

### 2단계 — main을 배포 기록으로 재정의

- main에 직접 커밋하지 않는다. 승격 머지와 hotfix만 받는다.
- dev 환경 배포 트리거를 `develop` → `dev` 브랜치로 정리한다.
- hotfix를 운영 태그에서 자르는 절차를 적용한다.
- 미완성 기능을 dev에 올리지 않는 규칙을 합의한다.

### 3단계 — 안정화

- 2~3회 릴리스 동안 백머지 누락 건수, 미승격 커밋 수, 롤백 발생 여부, 릴리스 소요 시간을 지표로 본다.
- 누락이 실제로 발생했으면 검사를 차단 모드로 올린다.
- 문제가 없으면 test 브랜치를 삭제한다.

### 롤백 계획

전환 중 문제가 생기면 브랜치가 아직 살아 있으므로 기존 파이프라인으로 되돌린다. 0단계에서 만든 승격 잡은 그대로 두고 트리거만 원복하면 된다. **브랜치 삭제를 3단계까지 미루는 이유가 이것이다.**

### 확인이 필요한 항목

| 항목 | 확인 대상 |
|---|---|
| 레지스트리에서 digest 기반 배포가 가능한지 | 인프라 |
| 파이프라인이 후보 커밋 SHA를 보관·조회할 수 있는지 | 인프라 |
| DB 마이그레이션 롤백 정책 (승격 시 스키마 호환성) | DBA |
| 릴리스 태그 생성 권한을 누구에게 줄지 | 조직 |
| 긴급 hotfix 승인자 지정 | 조직 |
| QA 평균 소요 기간 (릴리스 브랜치 필요 여부 판단 근거) | QA |
| 전환 시작 시점 (스프린트 경계 권장) | 팀 |

## 정리

- 브랜치로 환경을 표현하는 것을 그만두고, 같은 이미지를 승격해서 배포한다.
- 상시 브랜치는 `main`과 `dev` 둘. hotfix와 feature는 목적을 다하면 지운다.
- 릴리스는 브랜치를 자르는 게 아니라 **후보 커밋을 고정**하는 것으로 한다.
- `main`은 배포된 것만 받는다. 직접 커밋하지 않으므로 main 이력이 곧 배포 이력이 된다.
- 감시할 백머지는 `main → dev` 한 방향뿐이다. 관측부터 시작해서 필요하면 차단으로 올린다.
- 미완성 기능은 dev에 올리지 않는다. 대신 작업을 작게 쪼갠다.
- 파이프라인을 먼저 만들고 브랜치를 나중에 정리한다.
