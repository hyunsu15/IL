## 코드 위치

이 문서에서 다루는 실행 가능한 예제 코드(repo-facade)는 아래 저장소로 이관했다.

- https://github.com/hyunsu15/spring-c-layer

이 폴더에는 문서와 핵심 뼈대코드(뼈대코드 폴더)만 남겨둔다.

## 해당 내용을 다루게 된 계기

회사에서 C -> Java로 이전하는 작업을 하고 있다. 회사에서 겪은 시행착오가 작성하는 것이 좋다고 생각했다.

큰 줄기로는 Spring과 Mybatis를 사용하고 있습니다.요구사항은 기존 개발자들을 위해 최대한 C처럼 코드짜기이다.

아무래도 회사는 C위주 개발자다보니 자바 exception에 대한 해석을 이상하게 하여, 자바 코드가 기괴해진 경우가 있었다. 
예를들면, common -> 중간서비스-> 서비스 이 구성되어있을때, DataAcessException이나 비어있을때 무조건 예외를 던지게 되어있다.
그러다보니 중간서비스, 서비스는 try,catch에 의존적인 코드가 되고, 코드가 상당히 기형적이다. 차라리 C코드가 읽기 쉽다.


## 기형적으로 된 원인

자바에선 실패시 exception으로 처리한다. 이 내용을 spring과 기존 프로젝트의 차이에 대한 고민없이 쓰다보니 생긴 원인이라고 생각한다.


## 해결방안

우선 수정을 덜하게 한다면, 예외보단 객체로 내야하는 이유.md 파일에 작성대로 마지막 서비스를 제외하곤 객체로 값을 만들어야한다고 생각한다. 해당 내용은 내가 초안을 작성하고, ai로 검토를 시켰다.

그다음으로 가장 근본적인 해결방법은 파사드 빈을 자동으로 만들어준 기능이라고 생각한다.
try,catch를 최소화하면서 C코드와 호환성이 가장 높은 방식이라고 생각한다. 또한 일관성을 높일수 있다. 해당 방식은 해당 폴더에 둘생각이다.
또한 관련 문제를 풀면서 필요한 문서도 정리할 예정이다.

현재 생각하는 정답은 [spring-c-layer](https://github.com/hyunsu15/spring-c-layer) 저장소에 있는 것처럼 파사드빈을 활용하는 것이다.
가장 좋은 것은 스프링에 맞게 예외체계를 만드는 것도 좋아보이지만, 레거지 특성상 어디서 어떻게 터질지 모르기에, 복잡하지만 c 스타일 코드를 최대한 살리는 방식이 나아보임.


또한 common-> 중간서비스 -> 서비스에서 중간마다 체크하는 로직도 core.data에 있는 DataResultWrapper<T>와 비슷하게 반환 값을 반환하여, c와 유사하게 전략을 구사한다. 현재 DataResultWrapper는 데이터베이스 관련 결과 객체이다.

실제 프로젝트를 한다면, 패키지를 분리하고(core.data 처럼) 용도에 맞는 다른 결과 객체를 만들어서 사용하면 될 것 같다.
