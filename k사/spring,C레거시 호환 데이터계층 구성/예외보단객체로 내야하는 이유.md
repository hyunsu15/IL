# 예외보단 객체로 내야 하는 이유

## 1. 원래 스프링은 예외를 던지고, 잡지 않습니다

스프링을 잘 쓴다면 비즈니스 로직에서는 예외를 던지기만 하고, 중간에서 잡지 않습니다. `@RestControllerAdvice`(ExceptionHandler)가 마지막에 한 번에 받아서 응답으로 바꿔주기 때문입니다. 그래서 서비스 코드에는 try-catch가 거의 없는 깔끔한 코드가 됩니다.

예시 (일반적인 스프링 스타일)

```java
// 서비스: 던지기만 하고 잡지 않는다
@Service
public class OrderService {
    public Order order(Long userId, Long itemId) {
        Item item = itemRepository.findById(itemId)
                .orElseThrow(() -> new ItemNotFoundException(itemId));
        if (item.isSoldOut()) {
            throw new SoldOutException(itemId);
        }
        return orderRepository.save(Order.of(userId, item));
    }
}

// 예외 처리: 한 곳에서만 잡는다
@RestControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(SoldOutException.class)
    public ResponseEntity<ErrorResponse> handleSoldOut(SoldOutException e) {
        return ResponseEntity.status(HttpStatus.CONFLICT)
                .body(ErrorResponse.of("SOLD_OUT", e.getMessage()));
    }
}
```

## 2. 하지만 저희 코드는 중간중간 잡고 확인하는 로직이 많습니다

저희 구조는 common → 중간서비스 → 서비스로 되어 있는데, 계층을 지날 때마다 관련 예외를 try-catch로 잡아서 확인합니다. 예외를 "던지고 끝"이 아니라 **"던지고, 바로 위에서 잡고, 분기하고, 다시 던지는"** 식이라, 차라리 예외를 안 쓰는 게 낫겠다 싶을 정도로 try-catch가 많습니다.

예시 (현재 코드 패턴, 실제 코드는 사내 예시로 교체)

```java
// 중간서비스: 잡고 → 분기하고 → 다시 던진다
public XxxDto process(XxxRequest req) {
    try {
        CommonResult r = commonService.call(req);
        // ...
    } catch (CommonException e) {
        if ("E001".equals(e.getCode())) {
            // 여기서 복구해서 계속 진행
        } else {
            throw e; // 복구 못 하면 다시 던짐
        }
    }
    // ...
}
```

이 구조는 예외의 단점과 try-catch의 단점을 동시에 냅니다.

- **가독성**: 잡는 코드가 계층마다 반복되어 정작 비즈니스 로직이 눈에 안 들어옵니다. 또 어떤 예외가 어디까지 올라오는지가 시그니처에 드러나지 않아, 구현을 열어봐야만 흐름을 알 수 있습니다.
- **트랜잭션 함정**: `@Transactional`이 걸린 내부 호출에서 RuntimeException이 트랜잭션 경계를 넘으면 rollback-only가 마킹됩니다. 바깥에서 잡고 복구해도 커밋 시점에 `UnexpectedRollbackException`이 터질 수 있습니다. "분명히 catch 했는데 왜 롤백되지?"가 대부분 이 경우입니다.
- **비용**: 예외는 생성 시점에 스택트레이스를 만들기 때문에 일반 리턴보다 비쌉니다. 다만 DB I/O가 있는 일반 요청에서는 체감이 어렵고, 루프·배치처럼 반복 호출되는 곳에서 유의미합니다. 주된 근거라기보다 부수 효과입니다.

즉 "던지고 안 잡는" 예외의 장점은 못 쓰면서, 단점만 계층 수만큼 쌓이는 구조입니다.

## 3. 그렇다고 전부 스프링 스타일로 바꾸는 것은 리스크가 있습니다

그렇다고 완전한 스프링 스타일(던지고 ExceptionHandler에서만 잡기)로 바꾸는 것은 위험합니다.

- 저희 프로젝트는 **기존 동작하는 서비스와의 호환성이 1순위**입니다. 중간에서 잡아서 복구·분기하던 로직이 사라지면 기존과 다른 응답이나 동작이 나올 수 있습니다.
- 중간 계층의 catch는 단순 로깅이 아니라 실제 분기(복구, 대체 흐름)를 담당하는 경우가 많아서, 일괄 제거가 아니라 하나씩 검증하며 바꿔야 하는 작업입니다. 범위 대비 이득이 크지 않습니다.
- catch 제거는 **컴파일 에러 없이 조용히 동작이 바뀌는 변경**입니다. 빠뜨린 곳을 컴파일러가 못 잡아주고, 테스트나 운영에서야 드러납니다.

## 4. 그래서 예외는 마지막 서비스에서만 쓰는 것을 제안합니다

- **common, 중간서비스**: 예외 대신 성공/실패를 담은 **결과 객체를 반환**합니다. 호출자는 지금처럼 결과를 보고 분기하므로 기존 동작 호환성이 유지되고, try-catch만 사라집니다.
- **마지막 서비스**(컨트롤러가 직접 호출하는, 응답을 만드는 계층): 결과 객체를 확인해서, 실패면 그때 예외로 변환해 던지고 ExceptionHandler가 응답을 만듭니다. 스프링 스타일의 장점(공통 응답 처리)은 여기서 챙깁니다.

결과 객체 예시

```java
public record ServiceResult<T>(boolean success, ErrorCode code, String detail, T data) {
    public static <T> ServiceResult<T> ok(T data) { return new ServiceResult<>(true, null, null, data); }
    public static <T> ServiceResult<T> fail(ErrorCode code, String detail) {
        return new ServiceResult<>(false, code, detail, null);
    }

    @Override
    public T data() {
        // 실패 결과의 data를 읽으면 조용한 null 대신 그 자리에서 터뜨린다
        if (!success) throw new IllegalStateException("실패 결과에서 data 접근: " + code);
        return data;
    }
}
```

`data()`를 오버라이드한 이유: 실패 결과에서 `data()`를 그냥 null로 돌려주면, success 확인을 빠뜨린 코드가 **엉뚱한 곳에서 NPE**로 터집니다. 실패 지점에서 즉시 터뜨려야 원인을 바로 찾을 수 있습니다.

실패 코드는 문자열("E001")이 아니라 **enum**으로 둡니다. 오타가 컴파일 에러로 잡히고, IDE에서 사용처 추적이 됩니다. 단, 전사 공용 모듈에 거대 enum 하나로 두면 모든 도메인의 수정이 한 파일에 몰려 병목이 되므로, **공통 인터페이스 하나를 두고 도메인별 enum이 구현**하는 구조를 권장합니다.

`detail`에는 실패 지점의 컨텍스트(어떤 값으로 실패했는지)를 담아, 마지막에 예외로 변환될 때 원인 추적이 가능하게 합니다. 주의: `detail`은 내부 값이 담기므로 **로그·예외 메시지용이지, 사용자 응답에 그대로 내보내면 안 됩니다**(내부 정보 유출). 응답에 나가는 문구는 ErrorCode에 매핑된 별도 메시지를 씁니다.

```java
// 중간서비스: try-catch 대신 결과로 분기
ServiceResult<CommonData> r = commonService.call(req);
if (!r.success()) {
    if (r.code() == ErrorCode.RECOVERABLE_XXX) {
        // 복구해서 계속 진행
    } else {
        return ServiceResult.fail(r.code(), r.detail()); // 그대로 위로 전달
    }
}
```

```java
// 마지막 서비스: 여기서만 예외로 변환
ServiceResult<OrderData> r = middleService.process(req);
if (!r.success()) {
    throw new BusinessException(r.code(), r.detail()); // ExceptionHandler가 응답 처리
}
return OrderResponse.from(r.data());
```

자바 21 이상을 쓸 수 있다면 `sealed interface` + record + switch 패턴매칭으로 실패 케이스별 타입을 나누는 것이 더 좋습니다. 실패 케이스가 추가될 때 처리 안 한 곳이 전부 컴파일 에러로 잡히기 때문입니다.

## 5. 적용 전략

- **신규 코드와 수정이 필요한 코드부터** 적용합니다. 잘 돌아가는 기존 코드를 일괄 마이그레이션하지 않습니다.
- 시그니처 변경(예외 → 결과 객체)은 호출부가 **전부 컴파일 에러로 드러나므로** 빠뜨릴 수 없습니다. 반면 catch 제거는 조용히 동작이 바뀝니다. 같은 "변경"이어도 리스크의 성격이 다릅니다.
- 반환값을 확인하지 않는 코드를 막기 위해 정적 분석(ErrorProne의 `@CheckReturnValue` 등)이나 코드리뷰 체크 항목을 같이 도입합니다.

## 6. 예상 반론과 답변

제안 검토 때 나올 만한 질문을 미리 정리했습니다.

**Q1. 결과 객체 전환도 시그니처 변경인데, 3번에서 말한 호환성 리스크와 뭐가 다른가?**
다릅니다. 시그니처 변경은 호출부가 컴파일 에러로 전부 드러나서 **놓친 곳이 존재할 수 없습니다.** catch 제거는 컴파일러가 아무것도 잡아주지 못하고 런타임에 조용히 동작이 바뀝니다. 또한 신규 코드부터 적용하므로 기존 코드의 동작은 건드리지 않습니다.

**Q2. 예외는 무시하면 위로 터지기라도 하는데, 결과 객체는 확인 안 하면 조용히 사라지지 않나?**
맞습니다. 이 제안의 실제 약점이고, 그래서 5번의 정적 분석·리뷰 규칙이 세트입니다. 자바 21 이상이면 sealed + switch로 케이스 처리를 컴파일러가 강제하게 할 수 있습니다.

**Q3. 기존에 예외 덕분에 자동 롤백되던 실패는 어떻게 되나?**
가장 조심해야 할 부분입니다. 예외를 결과 객체로 바꾸면 **롤백이 자동으로 되지 않아 부분 커밋**될 수 있습니다. 그래서 규칙을 하나 둡니다: **실패 시점 이전에 DB 쓰기가 있었고 그걸 되돌려야 한다면, 그 실패는 결과 객체가 아니라 예외로 던집니다.** 결과 객체는 "쓰기 전 검증 실패"나 "되돌릴 것이 없는 실패"에 씁니다. 전환 대상마다 이 기준으로 케이스를 확인해야 합니다.

**Q4. 결과 객체로 바꾸면 실패 지점의 스택트레이스가 없는데, 장애 추적은?**
비즈니스 실패는 "어디서 왜"가 code + detail로 충분하고, 실패를 만드는 지점에서 로그를 남기는 규칙으로 보완합니다. 단 로그는 **실패를 만든 지점에서 한 번만** 남기고, 위로 전달하는 계층에서는 다시 남기지 않습니다(실패 하나에 계층 수만큼 로그가 찍히는 중복을 막기 위해). 스택트레이스가 정말 필요한 시스템 장애(DB 다운, NPE 등)는 애초에 결과 객체 대상이 아니라 예외로 그대로 올라갑니다.

**Q5. try-catch가 if로 바뀔 뿐, 분기 코드는 그대로 아닌가?**
분기 자체는 사라지지 않습니다. 이 제안의 목적은 코드량 감소가 아니라 **위험 제거**입니다: 트랜잭션 부작용이 없고, 흐름이 시그니처에 드러나고, 분기가 값 비교라 예외 타입 계층에 의존하지 않게 됩니다.

**Q6. 배치, 스케줄러, MQ 컨슈머는 ExceptionHandler가 없는데?**
`@RestControllerAdvice`는 MVC 요청만 받습니다. HTTP가 아닌 진입점은 각자의 경계(배치의 스킵/재시도 정책, 리스너의 에러 핸들러)에서 실패 결과를 처리해야 하고, "마지막에 예외로 변환" 규칙은 HTTP 진입점에만 해당합니다. 오히려 중간 계층이 결과 객체를 반환하면 진입점마다 처리 방식을 다르게 가져가기 쉬워집니다.

**Q7. 과도기에 예외 방식과 결과 객체 방식이 섞이면 더 헷갈리지 않나?**
섞이는 기간은 불가피하고, 꽤 오래 갈 수 있다는 걸 인정해야 합니다. 대신 구분 기준이 명확합니다: **반환 타입이 `ServiceResult`면 신방식, 아니면 구방식** — 시그니처만 보면 어느 쪽인지 바로 알 수 있습니다. 기존 예외 던지는 common API를 자주 쓰는 곳은 결과 객체로 감싸는 어댑터를 하나 두면, 중간서비스부터는 한 방식으로 통일됩니다. 목표는 "전부 바꾸는 것"이 아니라 **신규 코드의 기본값을 바꾸는 것**입니다.

**Q8. 마지막 서비스에서 굳이 예외로 변환하나? 컨트롤러가 결과 객체를 보고 바로 응답을 만들면 되지 않나?**
그것도 가능합니다. 예외로 변환하는 이유는 실패 → 공통 응답 포맷 변환, 로깅, 모니터링이 **이미 ExceptionHandler에 모여 있어서** 그걸 재사용하는 게 컨트롤러마다 실패 매핑을 반복하는 것보다 낫기 때문입니다. 그런 공통 처리가 아직 없다면 결과 객체 → 응답 직접 매핑도 좋은 선택입니다. 핵심은 방식이 아니라 **"실패를 응답으로 바꾸는 곳이 한 곳"**이라는 점입니다.

## 정리: 계층별 규칙

| 상황 | 처리 |
|---|---|
| common, 중간서비스의 비즈니스 실패 (예상 가능, 되돌릴 쓰기 없음) | 결과 객체 반환 |
| 실패 이전의 DB 쓰기를 되돌려야 하는 경우 | 예외 (롤백 필요) |
| 마지막 서비스에서 받은 실패 결과 | 예외로 변환 후 throw → ExceptionHandler |
| DB 다운, 타임아웃 같은 시스템 장애 | 어느 계층이든 잡지 않고 그대로 올림 |
| 프로그래밍 오류 (불변식 위반 등) | 예외 (복구 대상이 아니라 고칠 버그) |

주의할 점 하나: 결과 객체도 남용하면 호출부마다 unwrap 코드가 붙어서 오히려 읽기 힘들어집니다. **계층 경계를 넘는 반환값에만** 쓰고, 계층 내부 private 메서드까지 전부 `ServiceResult`로 감쌀 필요는 없습니다.
