# ArgoCD / GitLab CI 실패 알림 → Mattermost 연동 가이드

해당 문서를 쓰게 된 계기는 빌드가 실패했는지 아르고 CD나 깃허브등을 수동으로 확인해야 하는 이슈가 있어서 메터모스트가 있으니 편하게 받아보면 좋을 것 같아서 제안하게 되었습니다.

ArgoCD 배포(sync)나 GitLab CI 빌드가 제대로 되지 않을 때, **Mattermost 채널로 자동 알림**을 보내는 방법을 정리한 문서입니다. 별도의 서버나 봇을 개발할 필요 없이 기존 도구의 기능만으로 구성합니다.

## 전체 구조

```
GitLab (소스/CI) ──push/merge──▶ 이미지 빌드
        │                          │ 실패 시
        │                          └────────▶ Mattermost (케이스 2)
        ▼
   매니페스트 저장소
        │
        ▼
     ArgoCD ──sync 실패 시──────────────────▶ Mattermost (케이스 1)
```

- **케이스 1**: ArgoCD가 클러스터에 배포하는 단계에서 실패(Sync Error, Health Degraded 등) → `argocd-notifications-controller`가 Mattermost로 알림.
- **케이스 2**: GitLab CI에서 이미지 빌드/테스트 단계가 실패 → GitLab이 Mattermost로 알림.

둘은 담당 지점이 다르므로, 필요에 따라 하나만 또는 둘 다 구성할 수 있습니다.

## 사전 준비: Mattermost Incoming Webhook 만들기

1. Mattermost에서 알림을 받을 **채널**을 하나 정합니다.
2. `Main Menu(≡) → Integrations → Incoming Webhooks → Add Incoming Webhook`.
   - System Console에서 **Incoming Webhooks 기능이 Enable** 되어 있어야 메뉴가 보입니다.
   - (관리자) `System Console → Integrations → Integration Management → Enable Incoming Webhooks = true`
3. 채널을 선택하고 생성하면 아래와 같은 **Webhook URL**이 발급됩니다.

   ```
   https://<mattermost-host>/hooks/xxxxxxxxxxxxxxxxxxxxxxxxxx
   ```

4. 이 URL은 비밀값이므로 노출되지 않게 관리합니다. (Kubernetes Secret / GitLab CI 변수 등)

> Mattermost의 Incoming Webhook은 **Slack 호환 페이로드**(`{"text": "..."}`)를 받습니다. 그래서 ArgoCD의 `webhook` 서비스로 JSON을 그대로 보내면 됩니다.

## 케이스 1. ArgoCD 배포(sync) 실패 알림

ArgoCD의 **Notifications** 기능(`argocd-notifications-controller`)을 사용합니다. 최신 ArgoCD에는 기본 포함되어 있습니다.

### 1) Webhook URL을 Secret에 저장

`argocd-notifications-secret`에 URL을 넣어 두고 ConfigMap에서 참조하면 안전합니다.

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: argocd-notifications-secret
  namespace: argocd
type: Opaque
stringData:
  mattermost-webhook-url: https://<mattermost-host>/hooks/xxxxxxxxxxxxxxxxxxxxxxxxxx
```

### 2) 서비스 · 템플릿 · 트리거 설정

`argocd-notifications-cm` ConfigMap에 아래 내용을 추가합니다.

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: argocd-notifications-cm
  namespace: argocd
data:
  # (a) Mattermost로 보낼 webhook 서비스 정의
  service.webhook.mattermost: |
    url: $mattermost-webhook-url        # Secret의 값을 참조
    headers:
    - name: Content-Type
      value: application/json

  # (b) 메시지 템플릿
  template.app-sync-failed: |
    webhook:
      mattermost:
        method: POST
        body: |
          {
            "text": ":x: **{{.app.metadata.name}}** 배포(sync) 실패\n상태: `{{.app.status.operationState.phase}}`\n메시지: {{.app.status.operationState.message}}\n<{{.context.argocdUrl}}/applications/{{.app.metadata.name}}|ArgoCD에서 보기>"
          }
  template.app-health-degraded: |
    webhook:
      mattermost:
        method: POST
        body: |
          {
            "text": ":warning: **{{.app.metadata.name}}** 상태 저하(Degraded)\nHealth: `{{.app.status.health.status}}`\n<{{.context.argocdUrl}}/applications/{{.app.metadata.name}}|ArgoCD에서 보기>"
          }

  # (c) 트리거
  trigger.on-sync-failed: |
    - when: app.status.operationState.phase in ['Error', 'Failed']
      send: [app-sync-failed]
  trigger.on-health-degraded: |
    - when: app.status.health.status == 'Degraded'
      send: [app-health-degraded]
```

### 3) Application에 구독(annotation) 추가

알림을 받고 싶은 Application 매니페스트에 annotation을 붙입니다.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: my-app
  namespace: argocd
  annotations:
    notifications.argoproj.io/subscribe.on-sync-failed.mattermost: ""
    notifications.argoproj.io/subscribe.on-health-degraded.mattermost: ""
spec:
  # ...기존 설정...
```

### 4) 적용

```bash
kubectl apply -f argocd-notifications-secret.yaml
kubectl apply -f argocd-notifications-cm.yaml
kubectl apply -f my-app.yaml   # 또는 annotation만 patch

# 컨트롤러 재기동(설정을 바로 반영하고 싶을 때)
kubectl rollout restart deploy/argocd-notifications-controller -n argocd
```

## OpenShift(OpenShift GitOps)에서 쓸 때

OpenShift에서 ArgoCD를 **Red Hat OpenShift GitOps 오퍼레이터**로 설치했다면 위 방법이 **그대로 호환**됩니다. 다만 아래 차이점만 챙기면 됩니다.

### 1) Notifications 컨트롤러를 먼저 켜야 함 (가장 중요)

OpenShift GitOps는 notifications 컨트롤러가 기본으로 꺼져 있습니다. **ArgoCD CR(Custom Resource)** 에서 활성화합니다.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: ArgoCD
metadata:
  name: openshift-gitops          # 기본 인스턴스 이름
  namespace: openshift-gitops     # 기본 네임스페이스
spec:
  notifications:
    enabled: true
```

또는 명령어 한 줄로:

```bash
oc patch argocd openshift-gitops -n openshift-gitops --type merge \
  -p '{"spec":{"notifications":{"enabled":true}}}'
```

이걸 켜면 오퍼레이터가 notifications 컨트롤러를 배포하고, `argocd-notifications-cm` ConfigMap과 `argocd-notifications-secret` Secret을 **자동으로 생성**해 줍니다. 우리는 거기에 내용을 추가하면 됩니다.

### 2) 네임스페이스가 다름

이 문서의 예시에서 `namespace: argocd` → **`namespace: openshift-gitops`** 로 바꿔서 적용하세요. (별도 인스턴스를 만든 경우 해당 네임스페이스)

```bash
# Secret에 웹훅 URL 추가
oc patch secret argocd-notifications-secret -n openshift-gitops --type merge \
  -p '{"stringData":{"mattermost-webhook-url":"https://<mattermost-host>/hooks/xxxxxxxx"}}'

# ConfigMap에 서비스/템플릿/트리거 추가 (oc edit 또는 oc apply)
oc edit configmap argocd-notifications-cm -n openshift-gitops
```

- ConfigMap/Secret은 오퍼레이터가 만든 것을 **수정(추가)** 하는 방식입니다. 사용자 정의 `service.*` / `template.*` / `trigger.*` 항목은 그대로 유지됩니다.
- `kubectl` 대신 `oc`를 써도 되고, `kubectl`도 그대로 동작합니다.

### 3) Application annotation은 동일

케이스 1의 `notifications.argoproj.io/subscribe...` annotation은 OpenShift에서도 완전히 동일하게 사용합니다.

### 4) 확인 및 주의사항

```bash
# 컨트롤러가 떠 있는지 확인
oc get pods -n openshift-gitops | grep notifications

# 로그 확인
oc logs deploy/openshift-gitops-notifications-controller -n openshift-gitops
```

- 컨트롤러/리소스 이름에 인스턴스 이름 접두사가 붙습니다 (예: `openshift-gitops-notifications-controller`).
- Mattermost가 클러스터 **외부**에 있다면 egress(방화벽/프록시) 정책상 해당 URL로 나가는 트래픽이 허용되는지 확인하세요. 사내 프록시를 쓰면 ArgoCD CR의 proxy 설정 또는 컨트롤러 환경변수(`HTTPS_PROXY`)가 필요할 수 있습니다.

## 케이스 2. GitLab CI 빌드 실패 알림

빌드/테스트 자체가 실패하는 건 ArgoCD가 아니라 **GitLab CI**가 감지합니다. 두 가지 방법 중 하나를 쓰면 됩니다.

### 방법 A. GitLab 기본 Mattermost 인테그레이션 (설정만으로 끝, 권장)

1. GitLab 프로젝트 → `Settings → Integrations → Mattermost notifications`.
2. **Webhook**에 위에서 만든 Mattermost Incoming Webhook URL 입력.
3. **Trigger**에서 `Pipeline`, `Failed pipeline` 등 원하는 이벤트 체크.
4. Test settings로 확인 후 저장.

코드 수정 없이 파이프라인 실패 시 자동으로 알림이 갑니다.

### 방법 B. `.gitlab-ci.yml`에서 직접 호출 (메시지 커스터마이즈 가능)

프로젝트 CI/CD 변수(`Settings → CI/CD → Variables`)에 `MATTERMOST_WEBHOOK_URL`을 (Masked, Protected) 추가한 뒤:

```yaml
notify_on_failure:
  stage: .post
  image: curlimages/curl:latest
  when: on_failure          # 앞 단계가 실패했을 때만 실행
  script:
    - |
      curl -s -X POST -H 'Content-Type: application/json' \
        --data "{\"text\": \":x: **${CI_PROJECT_NAME}** 파이프라인 실패\nBranch: \`${CI_COMMIT_REF_NAME}\`\nJob: ${CI_JOB_NAME}\n[파이프라인 보기](${CI_PIPELINE_URL})\"}" \
        "${MATTERMOST_WEBHOOK_URL}"
```

## 동작 확인 / 트러블슈팅

- **웹훅 단독 테스트**: 아래 명령이 채널에 메시지를 올리면 URL은 정상입니다.

  ```bash
  curl -i -X POST -H 'Content-Type: application/json' \
    --data '{"text": "테스트 알림 :white_check_mark:"}' \
    "https://<mattermost-host>/hooks/xxxxxxxx"
  ```

- **ArgoCD 알림이 안 올 때**
  - `kubectl logs deploy/argocd-notifications-controller -n argocd` 로그 확인.
  - Application에 `subscribe` annotation이 붙었는지 확인.
  - ConfigMap의 서비스 이름(`service.webhook.mattermost`)과 annotation의 서비스 이름(`...mattermost`)이 일치하는지 확인.
  - `$mattermost-webhook-url` 참조 시 Secret 이름이 `argocd-notifications-secret`인지 확인.
- **Mattermost 400/403 에러**: System Console에서 Incoming Webhook이 Enable인지, "Enable integrations to override usernames/channels" 여부, URL 오타를 확인합니다.
