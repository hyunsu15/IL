# 성능 최적화 방안 제안서

## 1. SQL 및 Redis 호출 최소화

### Redis 최적화
*   **현황:** Redis는 빠르지만, 스카우터(Scouter) 기록상 4회 호출 시 약 1ms 소요.
*   **문제:** 코드 구조에 따라 Redis를 N*4회 호출하는 경우가 많음.
    *   예: 종목 100개 × 4회 = **400회** → 회당 약 0.25ms로 **약 100ms**.
    *   Redis가 값을 꺼내는 시간은 µs 단위이며, 회당 시간 대부분은 **네트워크 왕복 대기**.
*   **제안:**
    *   Redis 호출 횟수 줄이기 → 아래 **방법 1(MGET / 파이프라인)**, **방법 2(로컬 캐시)**.
    *   **종목 데이터 평탄화(Flat Structure)** 적용을 통해 효율성 확보.

#### 방법 1. 호출 묶기: MGET / 파이프라인
**기대 효과:** 400회 왕복 → 1회 (약 100ms → 1~2ms)
**난이도:** 중간 (루프 구조 변경 필요)

*   **MGET:** 여러 키의 값을 명령 하나로 한 번에 조회. 같은 종류(키→값) 조회만 묶을 수 있음.
*   **파이프라인:** 여러 명령을 응답을 기다리지 않고 한꺼번에 보낸 뒤, 응답도 한꺼번에 받음. 서로 다른 종류의 명령을 섞을 수 있음.

**시간 흐름**

```
하나씩 (지금)  요청→←응답 요청→←응답 요청→←응답 ... ×400   ≈ 100ms
MGET           [키 400개]→ ←[값 400개]                      ≈ 왕복 1번
파이프라인     요청1 요청2 ... 요청400 → ← 응답1 ... 응답400  ≈ 왕복 1번
```

| 구분 | MGET | 파이프라인 |
| :--- | :--- | :--- |
| 묶을 수 있는 것 | 같은 종류 조회만 (키→값) | 아무 명령이나 섞어서 |
| Redis가 받는 것 | 명령 1개 | 명령 400개 (보내기·받기만 몰아서) |
| Spring 메서드 | `opsForValue().multiGet(keys)` | `redisTemplate.executePipelined(...)` |
| 어울리는 경우 | 종목마다 같은 형태의 키 1개 | 종목마다 서로 다른 조회 여러 개 |

**Before / After ① MGET** — 종목마다 같은 형태의 키를 조회할 때

| 구분 | Before (지금) | After (MGET) |
| :--- | :--- | :--- |
| 호출 방식 | 종목마다 `get(key)` | 키를 모아 `multiGet(keys)` 1번 |
| Redis 왕복 | 종목 수만큼 | 1회 |
| 예상 시간 (400회 기준) | 약 100ms | 약 1~2ms |
| 루프 구조 | 조회하면서 처리 | 키 수집 → 일괄 조회 → 처리 |
| 결과 매핑 | 바로 사용 | `keys`와 같은 순서(인덱스)로 매핑, 없는 키는 `null` |

```java
// Before: 종목마다 1번씩 → 종목 수만큼 왕복 (키 이름은 예시)
for (String code : stockCodes) {
    Object price = redisTemplate.opsForValue().get("stock:price:" + code);
    // ... 처리
}

// After: 키를 먼저 다 모아서 1번 왕복
List<String> keys = stockCodes.stream().map(c -> "stock:price:" + c).toList();
List<Object> prices = redisTemplate.opsForValue().multiGet(keys);
for (int i = 0; i < stockCodes.size(); i++) {
    Object price = prices.get(i); // keys와 같은 순서, 없는 키는 null
    // ... 처리
}
```

**Before / After ② 파이프라인** — 종목마다 서로 다른 조회를 4번씩 할 때

| 구분 | Before (지금) | After (파이프라인) |
| :--- | :--- | :--- |
| 호출 방식 | 종목마다 `get`, `entries`, `range` 등 4번 | 400개 명령을 `executePipelined` 안에서 한꺼번에 전송 |
| Redis 왕복 | 종목 수 × 4 (400회) | 1회 |
| 예상 시간 (400회 기준) | 약 100ms | 약 1~2ms |
| 루프 구조 | 조회하면서 처리 | 일괄 조회 → 결과 목록을 순서대로 처리 |
| 결과 매핑 | 바로 사용 | 요청 순서대로 담긴 목록에서 `종목 순번 × 4 + 조회 순번`으로 꺼냄 |

```java
// Before: 종목마다 서로 다른 조회 4번 → 400회 왕복 (키 이름은 예시)
for (String code : stockCodes) {
    Object price = redisTemplate.opsForValue().get("stock:price:" + code);
    Map<Object, Object> info = redisTemplate.opsForHash().entries("stock:info:" + code);
    Object volume = redisTemplate.opsForValue().get("stock:volume:" + code);
    List<Object> trades = redisTemplate.opsForList().range("stock:trades:" + code, 0, 9);
    // ... 처리
}

// After: 400개 명령을 한꺼번에 보내고 결과를 한꺼번에 받음 → 왕복 1회
List<Object> results = redisTemplate.executePipelined(new SessionCallback<Object>() {
    @Override
    @SuppressWarnings("unchecked")
    public <K, V> Object execute(RedisOperations<K, V> operations) {
        RedisOperations<String, Object> ops = (RedisOperations<String, Object>) operations;
        for (String code : stockCodes) {
            ops.opsForValue().get("stock:price:" + code);   // 여기서는 null 반환, 실제 값은 results로
            ops.opsForHash().entries("stock:info:" + code);
            ops.opsForValue().get("stock:volume:" + code);
            ops.opsForList().range("stock:trades:" + code, 0, 9);
        }
        return null; // 반드시 null 반환 (아니면 예외)
    }
});

// 결과는 요청 순서대로 담김: 종목 i의 j번째 조회 = results.get(i * 4 + j)
for (int i = 0; i < stockCodes.size(); i++) {
    Object price = results.get(i * 4);
    Map<Object, Object> info = (Map<Object, Object>) results.get(i * 4 + 1);
    Object volume = results.get(i * 4 + 2);
    List<Object> trades = (List<Object>) results.get(i * 4 + 3);
    // ... 처리
}
```

**주의**

*   **키를 미리 알아야 함:** "조회하면서 처리"하던 루프를 "키 수집 → 일괄 조회 → 처리" 순서로 바꿔야 함.
*   **결과는 순서로 매핑:** 응답이 요청 순서대로 오므로 인덱스로 종목과 맞춤. 파이프라인은 조회 종류가 바뀌면 인덱스 계산도 같이 바뀌므로 상수로 관리.
*   **너무 크게 묶지 않기:** 400개는 문제없음. 수만 개면 Redis가 명령을 하나씩 처리하는 구조라 다른 요청이 밀릴 수 있으므로 500~1000개씩 나눠 보냄.

#### 방법 2. 로컬 캐시 (Caffeine)
**기대 효과:** Redis 왕복과 JSON 역직렬화 제거 (400회 기준 약 100ms → 0.1ms 미만, 캐시 히트 시)
**난이도:** 낮음 (조회 메서드에 `@Cacheable` 추가)
**전제:** 데이터가 늦게 반영돼도 되는 경우에만 적용

*   자주 쓰는 데이터를 파드 메모리에 보관해 Redis를 거치지 않고 조회.
*   Caffeine 조회는 회당 수십~수백 ns → 400회도 0.1ms 미만.
*   Redis 값이 JSON이면 조회마다 하던 역직렬화도 사라짐 (4번 벤치마크 기준 400 × 약 2.1µs ≈ 0.8ms).
*   종목 루프 구조는 그대로 둬도 됨.

**적용 판단 기준: "이 값이 늦게 반영돼도 괜찮은가?"**

| 데이터 성격 | 로컬 캐시 |
| :--- | :--- |
| 종목 마스터·코드성 데이터 (하루 1회 정도 변경) | 적극 추천 |
| 장중에 몇 분 단위로 바뀌는 데이터 | 만료 시간을 짧게 두고 조건부 적용 |
| 실시간 시세·호가·잔고 | 비추천 (파드 8~12개가 서로 다른 값을 들고 있게 됨) |

**Before / After**

| 구분 | Before (Redis 직접 조회) | After (로컬 캐시) |
| :--- | :--- | :--- |
| 조회 위치 | 매번 Redis (네트워크 왕복) | 파드 메모리 |
| Redis 왕복 (400회 기준) | 400회 | 0회 (캐시 히트 시) |
| 예상 시간 | 약 100ms | 0.1ms 미만 |
| 역직렬화 | 조회마다 발생 | 없음 (객체 그대로 보관) |
| 코드 변경 | — | 조회 메서드에 `@Cacheable` 추가 |
| 데이터 신선도 | 항상 최신 | 만료 시간만큼 늦을 수 있음 |
| 파드 간 일관성 | 모든 파드가 같은 값 | 파드마다 다를 수 있음 |

```java
// Before: 호출할 때마다 Redis 왕복
public StockInfo getStockInfo(String code) {
    return (StockInfo) redisTemplate.opsForValue().get("stock:info:" + code);
}

// After: 같은 메서드에 캐시만 추가 (호출부·루프는 그대로)
@Cacheable(cacheNames = "stockInfo", key = "#code")
public StockInfo getStockInfo(String code) {
    return (StockInfo) redisTemplate.opsForValue().get("stock:info:" + code);
}
```

```yaml
# @EnableCaching + caffeine 의존성 추가 후
spring:
  cache:
    type: caffeine   # Redis 의존성이 있으면 Redis 캐시가 먼저 잡히므로 지정 필요
    cache-names: stockInfo
    caffeine:
      spec: maximumSize=10000,expireAfterWrite=10m,recordStats
```

**주의**

*   **캐시된 객체 수정 금지:** Redis는 조회마다 새 객체를 주지만, 로컬 캐시는 모든 요청이 같은 인스턴스를 공유함. setter로 값을 바꾸면 다른 요청까지 오염되므로 불변 객체(record)로 보관하거나 복사본을 반환.
*   **파드 간 불일치:** 값이 바뀌면 만료 시간 동안 파드마다 다른 값을 가질 수 있음. 감수하거나, Redis pub/sub으로 각 파드의 캐시를 비움.
*   **같은 클래스 안 호출은 캐시 미적용:** `@Cacheable`은 프록시로 동작하므로 같은 클래스 내부에서 호출하면 캐시를 거치지 않음 → 별도 빈으로 분리.
*   **만료 순간 몰림:** 만료 시점에 요청이 Redis로 몰리면 `refreshAfterWrite`로 백그라운드 갱신 검토.
*   **힙 사용량:** 종목 수천 개면 수십 MB 이하지만 `maximumSize` 상한은 반드시 둠. 2번(GC) 검토 시 늘어난 메모리 반영.
*   **효과 측정:** `recordStats`로 히트율을 그라파나에서 확인.

#### 방법 1 · 2 시간 비교 (Redis 400회 기준)

| 방식 | Redis 왕복 | 예상 시간 | 지금 대비 |
| :--- | :---: | :---: | :---: |
| 지금 (하나씩 순차 호출) | 400회 | 약 100ms | — |
| 방법 1. MGET / 파이프라인 | 1회 | 약 1~2ms | 약 98ms 단축 |
| 방법 2. 로컬 캐시 (히트 시) | 0회 | 0.1ms 미만 | 약 100ms 단축 |

*   회당 0.25ms는 스카우터 "4회 ≈ 1ms" 기록에서 나눈 추정치. 스카우터는 ms 단위로 기록하므로 반올림을 감안하면 400회는 **40~160ms** 범위. 실제 400회를 호출하는 요청의 XLog에서 Redis 시간을 합산해 확정할 것.
*   방법 1을 이미 적용했다면 방법 2와의 차이는 1~2ms라 속도로는 고를 이유가 없음. 아래 기준으로 선택.

| 기준 | 방법 1. 호출 묶기 | 방법 2. 로컬 캐시 |
| :--- | :--- | :--- |
| 적합한 데이터 | 시세처럼 자주 바뀌는 데이터 | 종목 마스터처럼 드물게 바뀌는 데이터 |
| 데이터 신선도 | 항상 최신 | 만료 시간만큼 늦을 수 있음 |
| 코드 변경 | 루프 구조 변경 (키 수집 → 일괄 조회) | 조회 메서드에 `@Cacheable` |

### SQL 최적화
*   **지양할 패턴:** SQL 안에 SQL이 중첩되는 구조 (Nested SQL).
*   **제안:**
    *   중첩 구조를 피하고, 단일 쿼리나 조인(JOIN)으로 처리.
    *   종목마다 반복 호출하는 조회는 **IN으로 묶어서 조회** (아래 참고).
    *   **원칙:** OOM(Out Of Memory, 메모리 부족)이 발생하지 않는 선에서 SQL 호출 횟수를 최소화.

#### IN으로 묶어서 조회
*   종목마다 1번씩 하던 조회를 종목코드를 모아 `IN (...)` 한 번으로 처리 → 왕복 횟수 감소.
*   기존 쿼리는 그대로 두고 IN 조회 쿼리 하나만 추가하므로, JOIN보다 변경 범위가 작음.
*   **고정 크기로 잘라서 조회** (예: 20개씩): 종목 100개 기준 100회 → 5회로, 효과의 대부분을 확보.
*   **적용 대상:** 스카우터에서 "호출 횟수 × 시간" 상위 쿼리만. 늦게 반영돼도 되는 데이터는 로컬 캐시가 우선.

```xml
<select id="selectByCodes" resultType="StockInfo">
  SELECT STOCK_CD, STOCK_NM /* ... */
    FROM STOCK_MASTER
   WHERE STOCK_CD IN
   <foreach collection="codes" item="code" open="(" separator="," close=")">#{code}</foreach>
</select>
```

**주의**

*   Oracle은 IN 목록이 최대 1000개 (ORA-01795).
*   결과 순서가 보장되지 않으므로 순서가 아닌 종목코드로 매핑 (`@MapKey("stockCd")`).
*   마지막 묶음은 마지막 값을 반복해 크기를 채우면 SQL 문장이 1종류로 유지되어 Oracle 파싱 부담이 줄어듦.

## 2. 가비지 컬렉션(GC) 전략 변경: ZGC 고려
**기대 효과:** P99(최악 1%) 응답 속도 개선 (ms 단위)

### GC 모드 비교
*   **기존 모드 (Serial, Parallel, G1):**
    *   가비지 정리 시 **STW(Stop The World)** 발생으로 서비스 일시 중단.
    *   JDK 21 기본 정책: CPU 1개 이하 또는 메모리 1792MB 이하일 경우 Serial, 그 외 G1 선택.
*   **신규 후보 (ZGC, Shenandoah):**
    *   **특징:** STW 없이(또는 극소화하여) 실시간으로 가비지를 정리.
    *   **장점:** P99 응답 시간 개선에 유리.
    *   **단점:** CPU 및 메모리 사용량이 다른 모드보다 약간 높음.
    *   **추천:** Red Hat 계열 JDK 사용 중이므로 **Shenandoah** 적용도 유효.
    *   **팁:** ZGC 선택 시 세대(Generation) 모드를 함께 적용하면 효율이 더 높아짐.

넷플릭스 사례를 보면, 충분히 도입해볼 가치가 있어보임. 개발서버부터 점차적으로 도입해보는 것을 권장.

## 4. ObjectMapper Blackbird 모듈 추가
**기대 효과:** 성능 개선 미미 (추정 5ms 이하)
**추천 여부:** 적용 추천 (설정 편의성 높음)
