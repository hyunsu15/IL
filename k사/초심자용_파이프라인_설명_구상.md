# 초심자용 파이프라인 설명 — 큰 틀 구상안

> 작성일: 2026-10-06
> 대상: C2Java 변환 파이프라인을 처음 접하는 사람에게 설명할 자료(문서/발표)의 **구성안**
> 참고 기존 자산: [docs/manual/00_overview.md](manual/00_overview.md), [docs/파이프라인_흐름도.html](파이프라인_흐름도.html), `변환프로그램_설명자료_쉬운편.pptx`

## 0. 먼저 깔고 가는 전제

초심자 설명에서 제일 흔한 실패는 **단계를 순서대로 나열하는 것**이다.
8단계를 1번부터 8번까지 설명하면, 듣는 사람은 3번쯤에서 "그래서 이게 왜 필요한데?"를 놓치고
끝까지 못 따라온다.

그래서 틀을 **"단계 나열"이 아니라 "하나의 질문에 답해가는 구조"**로 잡는다.

그 질문은 이것이다.

> **"AI한테 C 코드 던지고 Java 받으면 되는 거 아냐? 왜 공정이 8단계나 돼?"**

초심자가 실제로 품는 의문이 이것이고, 이 시스템 전체가 바로 이 질문에 대한 답이다.
모든 장이 이 질문의 일부를 답하는 식으로 배치되면 중간에 이탈하지 않는다.

## 1. 설계 원칙 4가지

### ① 스포일러를 맨 앞에 — 결론 먼저, 근거는 나중

"전체 공정 중 LLM이 개입하는 곳은 **단 한 칸**"이라는 사실을 첫 화면에 박는다.
이것이 이 시스템의 정체성이고, 나머지 설명 전부가 "왜 한 칸뿐인가"의 해설이 된다.
(흐름도 HTML이 이미 이렇게 하고 있으며, 이 축을 더 밀어도 된다.)

### ② 나선형 — 같은 내용을 해상도 3단계로 3번 반복

| 바퀴 | 해상도 | 소요 |
|---|---|---|
| 1바퀴 | 한 문장 | 30초 |
| 2바퀴 | 비유로 | 3분 |
| 3바퀴 | 실제 단계·파일명으로 | 15분 |

초심자는 한 번에 못 받아들인다. 같은 것을 세 번 돌되 매번 해상도를 올리면,
중간에 이해를 놓쳐도 다음 바퀴에서 회수된다.

### ③ 비유를 하나만 정해서 끝까지 밀기

비유를 섞으면 망한다. "자동 변환 **공장**"으로 이미 잡혀 있으니 그것을 써도 되지만,
**번역 출판사**가 더 잘 맞는다. 각 단계가 1:1로 대응되기 때문이다.

| 파이프라인 | 번역 출판사 |
|---|---|
| 룰 카탈로그 (`rules/*.yaml`) | 용어집 + 문체 가이드 |
| 의존 분석 (`units.json`) | 원고를 장·절로 쪼개기 |
| 스캐폴드 (`signatures.json`) | 목차와 챕터 제목을 먼저 확정 |
| **유닛 변환 (LLM)** | **번역가 — 문단 하나씩만 맡김** |
| fixer (micro-repair) | 교정교열 담당 |
| 룰 기반 채점 | 편집장 검수 (용어집 기준으로) |
| Best-of-N | 번역가 3명에게 맡겨 제일 나은 것을 채택 |

> **"번역가에게 책 한 권을 통째로 주고 '알아서 잘해줘' 하지 않는다"**
> — 이 한 문장이 전체 설계 철학을 설명한다.

### ④ 추상 절차도보다 구체적 1건 추적

`MODULE_B` 모듈 하나를 골라 입력 C 파일부터 최종 Java·점수까지 **실제 파일을 보여주며**
끝까지 따라간다. 초심자는 "8단계가 있다"보다 "이 파일이 저 파일이 됐다"를 훨씬 잘 흡수한다.

## 2. 추천 목차 (7장)

| 장 | 제목 | 한 줄 메시지 | 분량 |
|---|---|---|---:|
| 1 | 왜 이걸 만들었나 | 수십 년 된 C 코드 수백 개를 사람이 다 옮길 수는 없다 | 5% |
| 2 | 한 문장 요약 + 지도 | **LLM은 8단계 중 1칸에서만 일한다** | 10% |
| 3 | 먼저 알 단어 6개 | 모듈 / 유닛 / 회차 / 스캐폴드 / 룰 / fixer | 10% |
| 4 | 비유로 한 바퀴 | 번역 출판사 공정에 그대로 대응시키기 | 15% |
| 5 | **MODULE_B 따라가기** | 실제 파일이 어떻게 변해가는지 1건 추적 | **35%** |
| 6 | 왜 이렇게까지 하나 | AI가 틀릴 여지를 앞뒤에서 좁히는 설계 | 15% |
| 7 | 직접 돌려보기 | `make new` → `make all MOD=... N=3` → 점수 확인 | 10% |

**5장이 전체의 1/3을 먹는 것이 핵심이다.**
나머지 장은 전부 5장을 읽히기 위한 준비이거나 복기다.

## 3. 장별로 꼭 들어가야 할 것

### 2장 — 지도

`docs/manual/00_overview.md`의 mermaid를 그대로 쓰지 말고,
**⓪① vs ②③④를 시각적으로 분리**한다.

- ⓪① : 자료가 바뀔 때만 돌리는 **준비 작업**
- ②③④ : `make all` 한 번에 매번 도는 **본 공정**

성격이 완전히 다른데 한 줄로 이어 그리면 초심자는 8단계를 매번 손으로 돌리는 줄 안다.

### 5장 — 1건 추적 (가장 중요)

각 단계마다 **들어간 것 → 나온 것**을 실제 파일로 보여준다.

```
MODULE_B_APS.pc (C 원본)
  → units.json        "함수 23개로 쪼갰습니다"
  → signatures.json   "클래스/메서드 이름을 미리 확정했습니다"   ← 여기까지 LLM 없음
  → [LLM] 유닛 하나씩 본문만 채움
  → postprocess_report.json / micro_repair_report.json  "자동으로 N군데 고쳤습니다"
  → summary.json      "78점"
```

> 실제 경로·파일 목록은 **부록 A**에 실측값으로 정리해두었다.

여기서 꼭 짚을 포인트 두 개:

1. **단계끼리 직접 대화하지 않고 항상 파일로 주고받는다**
   → 그래서 중간부터 재개(`RESUME=1`)가 되고, 어디서 틀렸는지 추적이 된다.
2. **LLM에게 주는 프롬프트의 빈칸이 얼마나 좁은지**를 실제 프롬프트 일부로 보여준다.
   ```bash
   make prompt MOD=MODULE_B TS=preview
   ```

### 6장 — 설계 이유

여기서 "왜 한 칸뿐인가"에 최종 답을 한다. 세 가지로 정리된다.

- **충실성** — 결정론적으로 바꿀 수 있는 것은 스크립트가 한다. AI가 "개선"하면 안 되니까.
- **재현성** — 같은 입력이면 비슷한 품질. 그래서 fixer는 멱등하고, 회차별로 산출물을 쌓는다.
- **온프레 제약** — 사내 Qwen3-Coder 80B가 주력. 모델을 못 바꾸니 **하네스 설계로 품질을 올린다**.

그리고 **"같은 룰 파일이 변환 지시서이자 채점 기준표"**라는 점 —
초심자에게도 바로 와닿는 설계 미학이라 꼭 넣는다.

## 4. 반드시 빼야 할 것

초심자용에서는 과감히 들어낸다. 이것들이 들어가면 절반이 이탈한다.

- 회차 관리의 세부 (`.seq` / `.current` / `TS` override 규칙) → "한 판에 번호 붙는다" 한 줄로 충분
- LLM 프로파일 3종 전환 (`claude_code.yaml` / `claude.yaml` / `inner_LLM.yaml`)
- 평가 가중치 100점의 세부 배분표 → "룰 기준으로 점수를 매긴다, 목표 75점" 정도만
- `repair` 루프 (어차피 `make all`에 포함되어 있지 않음)
- `all-pool`의 `reference/_pool` 제약 같은 운영 주의사항

전부 매뉴얼 2부(10~14장)와 06장으로 넘기고,
초심자 문서는 **"읽고 나면 `make all`을 돌려볼 수 있다"**까지만 책임지면 된다.

## 부록 A. 5장 원고 재료 — MODULE_B 실제 경로 추적

> 실측 기준 회차: `0020_20260903_module_b_t3of3`
> **회차 번호는 돌릴 때마다 바뀐다.** 문서에 쓸 때는 `0020_…`로 줄이고
> "← 본인 회차 번호로 바뀜"을 반드시 옆에 붙일 것. 안 그러면 고정 폴더명으로 오해한다.

### A-1. 읽기 전제 — 폴더 4칸의 역할

경로를 아무리 정확히 적어줘도 "이 폴더는 왜 있는가"를 모르면 외울 거리만 늘어난다.
**경로표보다 이 지도를 먼저 깐다.**

```
변환프로그램/
├── 1.원본소스/          ① 재료 — 바꿀 C 코드
├── workspace/
│   ├── runs/<회차>/     ② 작업대 — 이번 판에서 만든 모든 중간물
│   ├── candidates/      ③ 제출함 — 채점받을 최종본만 정리
│   └── eval/reports/    ④ 성적표 — 점수와 이유
└── archives/            ⑤ 보관함 — 판 통째로 백업(.tar.gz)
```

> 📚 **출판 비유** — ① 원서 · ② 작업실 책상(초고·교정지가 다 쌓임) · ③ 인쇄소에 넘길 완성 원고 ·
> ④ 편집장 검수 결과 · ⑤ 서고

**핵심 한 줄**

> `runs/`는 **과정이 전부** 남고, `candidates/`는 **결과만** 남는다.

이 구분만 잡히면 나머지는 따라온다.

### A-4. 하이라이트 — 32 vs 12

5장의 클라이맥스로 쓸 지점. 실측하면 이 두 숫자가 나온다.

| | 개수 |
|---|---:|
| `analysis/units.json`이 쪼갠 유닛 | **32개** |
| `unit_prompts/`에 실제로 생긴 프롬프트 | **12개** |

**20개가 비는데**, 유닛 종류를 까보면 이유가 보인다.

```
LOCAL 11 + SERVICE 1                        = 12   ← LLM이 번역한 것
MAPPER 7 · BSM 5 · SFW 4 · BCM 3 · AFW 1    = 20   ← 번역 안 함
```

뒤쪽 20개는 프레임워크 호출로 치환되거나 외부 모듈이라 애초에 번역 대상이 아니다.

> **쓸 말**
> 2장에서 "AI는 8단계 중 1칸에서만 일한다"고 했는데,
> **그 한 칸 안에서도 32개 중 12개만 만진다.**
> 설계 의도가 숫자로 증명되는 지점이다.

### A-6. 작성 시 주의

1. **회차 번호는 예시임을 명시한다** — `0020_…` + "본인 회차 번호로 바뀜"
2. **전체 트리를 한 번에 펼치지 않는다** — `unit_prompts/`만 해도 12개, `unit_logs/`도 12개다.
   `find` 결과를 그대로 붙이면 화면이 파일명으로 꽉 찬다.
   **폴더까지만 보여주고 "안에 유닛 수만큼 들어있습니다"**로 끝낸다.
3. **경로를 읽게 하지 말고 보게 한다** — 표의 오른쪽 열("열어보면")이 본문이고,
   왼쪽 경로는 나중에 찾아갈 때 쓰는 참조다. 설명할 때는 오른쪽을 읽는다.

## 부록 B. 비유를 더 밀 때 — 실제 번역 출판사 공정

4장·6장을 보강할 때 쓸 재료. 실제 산업 번역 표준(ISO 17100)의 공정은 다음과 같다.

```
Translation (번역)  →  Check (자가 점검)  →  Revision (타인 대조검수, 의무)
  →  Review (분야 전문가, 선택)  →  Proofreading (조판 후 최종, 선택)  →  Final verification
```

핵심은 **Revision이 의무이고, 번역한 사람이 할 수 없다**는 점이다.
자기가 만든 것을 자기가 검수하면 같은 착각을 반복하기 때문이다.

단행본 출판 번역에는 추가로 네 가지 장치가 있다.

1. **질의서(query sheet)** — 번역가는 애매한 것을 추측해 메우지 않고 "확인 필요"로 분리해 넘긴다.
2. **스타일시트** — 작업 중 내린 판단을 계속 적어 쌓아 다음 장에 적용한다.
3. **번역 메모리(TM)** — 승인된 번역을 자산으로 적재해 재사용한다.
4. **교정쇄(proof)** — 원고가 아니라 **실제 인쇄될 형태로 찍어서** 본다.

> **설명 자료에 쓸 때의 팁**
> 6장에서 "우리는 번역가 한 명한테 책을 통째로 안 맡긴다"고 자랑한 뒤,
> **"대신 우리에겐 아직 교정쇄(=컴파일 검증)가 없다"**까지 솔직하게 넣으면 신뢰도가 올라간다.
> 초심자용 문서가 자랑만 하면 오히려 덜 믿긴다.

※ 출판 공정과의 상세 대조 및 파이프라인 보강 제안(컴파일 검증·질의서·2차 검수 등)은 별도 검토 건으로 분리.
