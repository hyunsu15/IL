## 도입부(필요시)
이 프로젝트가 왜 존재할까요? 

수십 년 된 C 코드를 Java로 옮겨야 합니다. 사람이 손으로 하면 모듈 하나에 며칠, 전체로는 몇 달입니다. 

AI로 변환시 이러한 장점이 있습니다.
ex) AI로 변환시 인력대비 40% 감소된다.
- 우리가 예상하는 Man-hour 시간을 넣으면 더욱 설득력 있을 것으로 예상됨.

Java로 옮길 때, 장점이있습니다.
ex)Junit으로 빠른 단위테스트가 가능하다. 데이터 계층의 추상화로 DB 종속적이지 않다. 여러값을 반환받을때, fetch 문을 안써도 된다.

- Java로 옮길 때, 장점들을 간단히 나열하는 것도 설득력있어보임.
 

목표는 둘입니다.
**사람의 손을 줄이고, 동시에 AI에게 맡기는 범위도 좁히는 것.**
그 사이를 자동화된 스크립트가 메웁니다.


## 서두

그래서 C 코드를 Java로 바꾸는 공정을 만들었습니다. 그런데 8단계입니다.

**"AI한테 그냥 던지고 Java 받으면 되는 거 아냐? 왜 8단계나 필요해?"**

오늘은 이 질문에 답하는 순서로 가겠습니다.


## 한문장 요약 + 파이프라인 로드맵
LLM은 8단계 중 1칸에서만 일합니다. 나머지는 전/후처리로 AI 개

- 내부 자료 파이프라인 사진 첨부
- 예고편/간단 요약 느낌으로 서술


## 용어
### 모듈
변환 단위. C파일입니다. 
- 모듈명

### 유닛
모듈을 함수 단위로 쪼갠 최소 변환 단위. 모듈 하나에는 여러 유닛이 존재합니다. AI는 한번에 한 유닛만 변역합니다. 

### 회차
변환을 실행한 회차/번호.
- 이것을 모르면 결과물을 못 찾습니다. 그 판의 모든 산출물이 여기 쌓이기 때문입니다


### 스캐폴드

AI를 부르기 전에 미리 확정해 둔 Java 뼈대. AI는 뼈대 안의 본문만 채웁니다
- ex 클래스명·메서드명·인자·패키지.


### 룰 카탈로그

코딩 가이드 문서를 기계가 읽는 YAML로 정제한 것. 변환 지시서와 채점 기준표가 같은 파일이라 "가르친 것"과 "채점하는 것"이 어긋나지 않습니다.


### fixer

자주 나오는 오류 패턴을 AI 없이 문자열·구문 규칙만으로 고치는 자동 교정기.

## 둘러보기

미리했었던 내용을 보여준다. 각 단계마다 **들어간 것 → 나온 것**을 실제 파일로 보여준다.

변환프로그램 폴더 구조
```
변환프로그램/
├── 1.원본소스/          ① 재료 — 바꿀 C 코드
├── workspace/
│   ├── runs/<회차>/     ② 작업대 — 이번 판에서 만든 모든 중간물
│   ├── candidates/      ③ 제출함 — 모듈을 마지막으로 돌렸을 때의 결과물
│   └── eval/reports/    ④ 성적표 — 점수와 이유
└── archives/            ⑤ 보관함 — 판 통째로 백업(.tar.gz)
```


단계별 추적표
예시

| # | 단계 | 실제 경로 | 열어보면 |
|---|---|---|---|
| — | **원본** | `1.원본소스/ac/qry/MODULE_A_APS.pc` | 바꿀 C 코드 |
| 1 | **분해** | `모듈폴더/analysis/units.json` | **32개 유닛으로 쪼갰음** |
| | | `모듈폴더/analysis/call_map.json` | 누가 누굴 부르는지 |
| | | `모듈폴더/analysis/dependency_order.json` | 어떤 순서로 변환할지 |
| 2 | **뼈대** | `모듈폴더/analysis/signatures.json` | 클래스·메서드 이름 **확정** (LLM 호출 전) |
| 3 | **변환** | `모듈폴더/unit_prompts/*.md` (12개) | **LLM에게 실제로 보낸 지시문** |
| | | `모듈폴더/unit_logs/*.api.txt` | LLM이 뭐라 답했는지 원문 |
| | | `모듈폴더/units_status.json` | 유닛별 성공/실패 |
| | | `모듈폴더/java/src/main/java/…/service/MODULE_AService.java` | **완성된 Java** |
| 4 | **후처리** | `모듈폴더/postprocess_report.json` | import 정리 · 위반 플래그 |
| 5 | **교정** | `모듈폴더/micro_repair_report.json` | fixer가 고친 내역 |
| 6 | **정리** | `workspace/candidates/batch/모듈/src/` | 채점용 제출본 |
| 7 | **채점** | `workspace/eval/reports/<회차>/summary.json` | 영역별 점수 |
| | | `workspace/eval/reports/<회차>/detail/모듈__batch.md` | **왜 깎였는지** |
| | | `workspace/eval/reports/<회차>/dashboard.html` | 보기 좋은 요약 |
| 8 | **백업** | `archives/0020_20260903_모듈_t3of3.tar.gz` | 판 통째로 |

(표를 내용을 설명한 후)
**AI는 8단계 중 1칸에서 일하고, 그 1칸 안에서도 절반 이하만 만집니다.**

## 설계 이유

여기서 "왜 한 칸뿐인가"에 최종 답을 한다. 세 가지로 정리된다.

- **충실성** — 결정론적으로 바꿀 수 있는 것은 스크립트가 한다. 
- **재현성** — 같은 입력이면 비슷한 품질. 그래서 fixer는 멱등하고, 회차별로 산출물을 쌓는다.
- **온프레미스 제약** — 사내 Qwen3-Coder 80B가 주력. 모델을 못 바꾸니 **하네스 설계로 품질을 올린다**.

그리고 **"같은 룰 파일이 변환 지시서이자 채점 기준표"**
